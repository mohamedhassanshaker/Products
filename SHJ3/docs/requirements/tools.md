# 5.6 `tools` — skills, MCP servers, API connectors, resilience (B3 step 4, B5)

Configuration in `shj3-web`, execution in `shj3-ai`. Satisfies brief requirement R4.

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-TOOL-01 | The system shall maintain a platform-wide skills catalogue whose entries can be attached to or detached from an individual agent. | B3 step 4A; B5 tab 1 | MUST | The four seeded skills render with their seeded attachment states. Attaching a skill makes it callable by that agent only. |
| FR-TOOL-02 | The system shall display a live summary of attached catalogue skills, bound MCP tools and bound API connectors for the agent being edited. | B3 step 4A | MUST | The three counts update on every attach or detach without a page reload and agree with the underlying bindings. |
| FR-TOOL-03 | The system shall maintain an MCP server registry recording name, endpoint, authentication method and connection state. | B3 step 4B; B5 tab 2 | MUST | The two seeded servers render with `Connected` and `Not connected` states, their endpoints and their auth methods (OAuth2 client credentials, mTLS). |
| FR-TOOL-04 | The system shall connect to an MCP server and discover its exposed tools, recording the discovered tool set against that server. | B3 step 4B; B5 tab 2 | MUST | Connecting the Customs server discovers and persists `get_declaration_status`, `submit_customs_form`, `list_fees`. A failed connection leaves state `Not connected` and surfaces the failure reason. |
| FR-TOOL-05 | The system shall add a new MCP server given an endpoint and an authentication configuration, and shall discover its tools on connect. | B3 step 4B | MUST | A newly added server appears in the registry, and its discovered tools become individually bindable. Credentials are stored as secret references, never as configuration values (FR-TOOL-20). |
| FR-TOOL-06 | The system shall allow each discovered tool to be bound to or unbound from an agent independently of the other tools on the same server. | B3 step 4B | MUST | Binding `get_bill_status` does not bind `cancel_booking`. Bindings are per agent version, not per server. |
| FR-TOOL-07 | The system shall permit an agent to invoke only tools explicitly bound to it; discovery alone shall not confer callability. | B3 step 4 `[rule]` | MUST | An unbound but discovered tool is rejected at invocation with a permission error, and the attempt is recorded on the trace. This is the tool-permission boundary and is tested with a direct runtime invocation, not only through the UI. |
| FR-TOOL-08 | The system shall maintain an API connector registry recording name, HTTP method, endpoint, authentication method and test state. | B3 step 4C; B5 tab 3 | MUST | The two seeded connectors render with `Tested` and `Untested` states. Endpoint path parameters such as `{account}` are declared, not string-concatenated at call time. |
| FR-TOOL-09 | The system shall test an API connector on demand, updating its test state and returning a sample response body. | B3 step 4C | MUST | Testing the untested connector flips its state and displays the response. A failing test records the failure and does not mark the connector tested. |
| FR-TOOL-10 | The system shall add an API connector given a method, endpoint and authentication configuration. | B3 step 4C | MUST | A newly added connector is persisted, appears in both the wizard and the registry, and is untested until tested. |
| FR-TOOL-11 | The system shall expose every registered API connector as a callable skill carrying its own input/output schema and its own rate-limit policy. | B3 step 4 `[rule]` | MUST | Each connector has a declared schema used to validate arguments before the call. Exceeding the connector's rate limit fails the call fast with a distinguishable error rather than queueing indefinitely. |
| FR-TOOL-12 | The system shall present the wizard's tool configuration and the platform tools registry as two views over one data set, such that a change in either is immediately visible in the other. | B5 intro; [`cross-module.md`](./cross-module.md) | MUST | Binding a tool in the wizard is present in the registry on the next read with no synchronisation step, and the reverse. There is one write path and one store of record for bindings. |
| FR-TOOL-13 | The system shall configure a circuit breaker per external dependency, recording the failure threshold, the observation window, the cooldown period, the fallback behaviour and the current state. | B5 tab 4 | MUST | The three seeded breakers render with their seeded thresholds, cooldowns and fallbacks. The SEWA bill API breaker is seeded `Open — fallback active`. |
| FR-TOOL-14 | The system shall consult the relevant breaker before every outbound tool or connector call and shall serve the configured fallback without attempting the call when the breaker is open. | B5 tab 4 `[rule]` | MUST | With the breaker open, no outbound request is made and the fallback response is returned within the fast-fail budget. The decision is recorded on the trace. |
| FR-TOOL-15 | The system shall reset or manually trip a breaker for testing purposes, restricted to an authorised role and audited. | B5 tab 4 | MUST | Tripping the healthy gateway breaker causes the next call to take the fallback path. Both actions are audited with actor and target. |
| FR-TOOL-16 | The system shall optionally serve cached answers while a source is unavailable, honouring a maximum cache age, and shall not serve cached content older than that age. | B5 tab 4 | MUST | With caching on and the gateway breaker open, an answer under 24 hours old is served and labelled as cached; one older than 24 hours is not served and the degraded-mode path is taken instead. |
| FR-TOOL-17 | The system shall display a configurable degraded-mode message to the citizen when a dependency in the current journey is in fallback. | B5 tab 4 | MUST | With the SEWA breaker open, a billing conversation shows the configured degraded message and the assistant still answers non-payment questions. |
| FR-TOOL-18 | The system shall hold breaker state in Redis so that a breaker tripped by one replica is tripped for all replicas. | architecture §10 | MUST | Trip a breaker on replica A; replica B takes the fallback path on its next call without a restart or a local timer. |
| FR-TOOL-19 | The system shall record every tool invocation on the turn trace with the tool identity, the arguments passed, the outcome and the elapsed time. | A2; B4 | MUST | The seeded journey's trace records `get_bill_status(provider="SEWA")` with its outcome. Arguments are recorded post-PII-masking. |
| FR-TOOL-20 | The system shall store tool and connector credentials as references to a secret store and shall never return a credential value through an API or render it in the UI. | architecture §10 | MUST | Reading a connector's configuration returns a secret reference, never a key. No log line, error message or API response contains a credential. Secrets are absent from the database in plaintext. |
| FR-TOOL-21 | Tool bindings created in the agent wizard and tool bindings shown in the platform tools registry shall be one record set with one write path, such that neither view can hold a binding the other does not. | `agents` ↔ `tools`; B3 step 4 ↔ B5 | MUST | Bind a tool in the wizard, read the registry: present. Unbind in the registry, read the wizard: absent. A test asserts there is exactly one persistence path for a binding. No synchronisation job exists, because none is needed. *(Cross-module invariant; also listed in [`cross-module.md`](./cross-module.md).)* |
| FR-TOOL-22 | A dependency reported as degraded in observability and the state of that dependency's circuit breaker shall be two views of one state, never two independently maintained records. | `governance` ↔ `tools`; B14 tab 3 ↔ B5 tab 4 | MUST | The seeded SEWA bill API is `Degraded` in observability and `Open` in the breaker configuration, from one underlying state. Resetting the breaker changes the observability status once the error rate recovers. There is no path that produces `Healthy` alongside an open breaker. *(Cross-module invariant; also listed in [`cross-module.md`](./cross-module.md).)* |
