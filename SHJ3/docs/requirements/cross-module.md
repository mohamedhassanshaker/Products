# 6. Cross-module integration requirements

The wireframe is interconnected on purpose (guide §6). Each row of its wiring table is a **consistency invariant between two modules** — the highest-value tests in the system, because each one is where a plausible implementation silently diverges into two sources of truth.

These requirements carry IDs in the owning module's sequence and are also listed there. They do not restate the single-module behaviour; they require that the two sides cannot disagree.

| ID | Invariant | Modules / screens | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-TOOL-21 | Tool bindings created in the agent wizard and tool bindings shown in the platform tools registry shall be one record set with one write path, such that neither view can hold a binding the other does not. | [`agents.md`](./agents.md) ↔ [`tools.md`](./tools.md); B3 step 4 ↔ B5 | MUST | Bind a tool in the wizard, read the registry: present. Unbind in the registry, read the wizard: absent. A test asserts there is exactly one persistence path for a binding. No synchronisation job exists, because none is needed. |
| FR-CHAN-23 | Approving a message template shall unblock every campaign depending on it, and un-approving or withdrawing a template shall re-block them, evaluated from the template's current state rather than from a copied flag on the campaign. | [`channels.md`](./channels.md); B10 tab 3 → tab 4 | MUST | Approve `appointment_confirmation`: its campaign becomes enableable in the same read. Withdraw the approval: the campaign returns to `Blocked` and, if enabled, stops sending. The campaign record holds no duplicated approval state. |
| FR-IAM-18 | Team membership shall be a single derived projection of user team assignment, so a reassignment in the users view is immediately reflected in the teams view with no second write. | [`iam.md`](./iam.md); B9 tab 1 → tab 2 | MUST | Reassign a user from Libraries to Customs; both views agree on the next read. A test asserts no writable membership relation exists independently of the user record. |
| FR-GOV-29 | Approving or rejecting a promotion and writing its audit entry shall be one atomic operation, so no decision can exist without its audit entry and no audit entry without its decision. | [`governance.md`](./governance.md); B14 tab 1 → tab 2 | MUST | Approve the seeded promotion: the audit entry is present on the next read. Inject an audit-write failure: the decision is rolled back and the promotion remains pending. Counts of decisions and their audit entries are equal at all times. |
| FR-EVAL-14 | Adding a conversation to a golden set from the command centre shall increment that set's case count and create a case referencing the source conversation, with the two sides always consistent. | [`analytics.md`](./analytics.md) → [`evaluation.md`](./evaluation.md); B1 → B13 | MUST | Add a transcript to *Billing core journeys*: the count increases by one and the new case names the conversation. The set's stored count equals the number of its cases, asserted after a batch of additions. |
| FR-EVAL-15 | The publish gate shall read locale translation completeness from the channels module's live figure, and shall block a bound agent naming that locale and that percentage, so the two screens can never disagree about Arabic readiness. | [`channels.md`](./channels.md) → [`evaluation.md`](./evaluation.md); B10 tab 5 → B13 tab 3 | MUST | With Arabic at 82%, the gate blocks a bound agent naming Arabic and 82%. Raise Arabic to 100%: the gate stops blocking on that ground without any evaluation-side edit. The gate holds no copied percentage. |
| FR-TOOL-22 | A dependency reported as degraded in observability and the state of that dependency's circuit breaker shall be two views of one state, never two independently maintained records. | [`governance.md`](./governance.md) ↔ [`tools.md`](./tools.md); B14 tab 3 ↔ B5 tab 4 | MUST | The seeded SEWA bill API is `Degraded` in observability and `Open` in the breaker configuration, from one underlying state. Resetting the breaker changes the observability status once the error rate recovers. There is no path that produces `Healthy` alongside an open breaker. |
| FR-KNOW-26 | An unresolved source conflict shall reduce the grounding confidence of every answer touching the affected entity, by an amount capable of tripping the configured refusal policy, and resolving the conflict shall restore it. | [`knowledge.md`](./knowledge.md) → [`governance.md`](./governance.md); B6 tab 4 → B12 | MUST | With the tariff conflict unresolved and the threshold at 60%, a tariff question is refused and a human offered. Mark one side authoritative: the same question is answered. The confidence figure and the refusal decision are recorded on both traces. |
| FR-HAND-20 | A handover node firing in a flow shall create exactly one escalation ticket carrying the trigger that fired as its escalation reason, so the flow definition and the operational queue always agree. | [`flows.md`](./flows.md) → [`handover.md`](./handover.md); B7 → B8 | MUST | Fire the low-confidence trigger: one ticket appears with reason "low grounding confidence" and the measured confidence. Fire the tool-failure trigger: one ticket with reason "tool call failed twice". No ticket exists without a trigger, and no fired trigger exists without a ticket. |
| FR-HAND-21 | The rule tester shall evaluate the same ordered, enabled rule set that production routing evaluates, including changes not yet saved, so a tester result and a live routing decision cannot differ for identical input. | [`handover.md`](./handover.md); B8 within-screen | MUST | Reorder rules, run the tester, save, then route a real ticket with identical attributes: the outcomes match. A test drives the same input through both the tester and the routing path and asserts equality — the tester and the router share one evaluation implementation. |
| FR-FLOW-12 | A tool call failing twice within a flow shall produce the tool-failure escalation reason on the resulting ticket, carrying the failing tool's identity and both attempt outcomes. | [`flows.md`](./flows.md) → [`handover.md`](./handover.md); B7 → B8 | MUST | Force two `get_bill_status` failures: the ticket names the tool, both attempts and their errors. One failure produces no ticket. Three attempts never occur ([`flows.md`](./flows.md) FR-FLOW-05). |

## Delivery-added invariant — orchestration ↔ orchestration (legacy vs. pipeline)

The Pipeline Designer ([`orchestration.md`](./orchestration.md) §5.5.2) introduced one further cross-cutting invariant, within a single module rather than between two, recorded here because it is exactly the same class of risk as the rows above: a plausible implementation could let two configuration surfaces both believe they govern the same turn.

| ID | Invariant | Modules / screens | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-ORCH-26 | While a tenant has an active pipeline, the legacy execution-mode controls shall render disabled under an explanatory notice, and the two configuration surfaces (legacy `executionMode` and the active `PipelineVersion`) can never simultaneously claim authority over the same turn's execution shape. | [`orchestration.md`](./orchestration.md) §5.5.1 ↔ §5.5.2 | MUST | See [`orchestration.md`](./orchestration.md) FR-ORCH-26 for full detail. `process_turn.py` branches deterministically on `RouterConfig.activePipelineVersionId`, never on both paths' configuration simultaneously. |
