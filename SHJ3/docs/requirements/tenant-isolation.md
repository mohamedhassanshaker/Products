# 8. Tenant isolation requirements

**This is the requirement set that, if wrong, invalidates every other requirement in this document set.** A tenant is a Sharjah government entity. A cross-tenant leak in a government service is a confidentiality breach, not a defect, and the wireframe makes tenancy load-bearing in at least six places: agent ownership (B2), source ownership (B6 tab 1), team entity scope (B9 tab 2), per-agent policy overrides (B12 tab 2), per-tenant erasure and residency (B14 tab 4), and per-tenant branding (Phase E) — plus, delivery-added, per-tenant pipeline designs (`orchestration.md` §5.5.2).

Isolation is designed so that a cross-tenant query **cannot be expressed**, not so that it is remembered against. Requirements below are the security properties; the mechanisms are [`platform.md`](./platform.md) FR-PLAT-01 to FR-PLAT-08.

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| NFR-SEC-15 | Isolation shall be per store: SQL Server schema per tenant, Qdrant collection per tenant, Redis key prefix per tenant — **physical in all three** — and, for Neo4j, **logical** partitioning by tenant label plus `tenant_id` property. | ADR-0002; **ADR-0009** | MUST | Each store's isolation unit exists per provisioned tenant. For the three physically isolated stores, a handle scoped to tenant A cannot address tenant B's unit at all. For the graph, every node carries both encodings and they agree; no cross-tenant edge exists; and a negative test exists **per graph query path** — see NFR-SEC-25. |
| NFR-SEC-25 | Graph tenant scoping shall be produced by a mandatory tenant-aware query builder, with raw Cypher forbidden outside the graph adapter and enforced by a static check, and with retrieval results re-filtered against the request tenant after leaving the graph. | ADR-0009 rules 1, 2, 4 | MUST | Application code cannot express an unscoped graph query. The build fails if a Cypher literal (`MATCH`, `MERGE`, `CREATE`, `CALL db.`) appears outside `adapters/outbound/graph/`. A graph result injected at the adapter boundary carrying a foreign `tenant_id` is dropped before it can ground an answer, proving the post-filter independently of the builder. |
| NFR-SEC-16 | The tenant shall be resolved from the authenticated principal only, never from a header, query string, route parameter or request body. | ADR-0002 rule 1 | MUST | Negative tests forge a tenant in each of the four locations for every mutating endpoint; each is ignored or refused, and none reaches a store. |
| NFR-SEC-17 | Tenant context shall be bound to the request scope and read by the data-access layer, not passed as an argument through application code. | ADR-0002 rule 2 | MUST | Application-layer functions take no tenant parameter. A test asserts that an async continuation, a background task spawned from a request, and a streamed response all carry the correct context. |
| NFR-SEC-18 | Unscoped store clients shall not be exported from any module; only tenant-scoped handle factories shall be available. | ADR-0002 rule 3 | MUST | No module exports a raw Prisma, Neo4j, Qdrant or Redis client. A search for such an export returns nothing in either runtime. An application author has no vocabulary in which to write a cross-tenant query. |
| NFR-SEC-19 | Store, database, collection and key-prefix names shall be derived from a slug validated against the tenant registry, and never interpolated from input. | ADR-0002 rule 4 | MUST | Enforced by [`platform.md`](./platform.md) FR-PLAT-03. An injection payload in a tenant field is rejected at validation, closing both the isolation and the injection path. |
| NFR-SEC-20 | Exactly two cross-tenant paths shall exist — tenant provisioning and cross-tenant analytics rollups — both in `platform`, both requiring `Super Admin`, both audited. | ADR-0002 rule 5 | MUST | Enforced by [`platform.md`](./platform.md) FR-PLAT-08. A test enumerates the route table and the data-access surface and finds no third path. |
| NFR-SEC-21 | Retrieval, embedding, graph traversal and cache access shall be tenant-scoped, so no citizen answer can cite, quote or embed another tenant's content. | ADR-0002 option B rejection | MUST | A retrieval in tenant A returns no passage, score, citation or entity from tenant B. This is tested directly against the derived stores, not only through the API, because retrieval output is what gets quoted back to a citizen. |
| NFR-SEC-22 | Tenant theming and branding shall never render to a principal of another tenant, including through a shared cache or a CDN. | Phase E; ADR-0007 | MUST | Loading the same route as principals of two tenants in sequence yields each tenant's own branding. No cache key omits the tenant. |
| NFR-SEC-23 | Retention, erasure and residency settings shall apply per tenant, and one tenant's setting shall never govern another's data. | B14 tab 4; ADR-0002 | MUST | Enforced by [`governance.md`](./governance.md) FR-GOV-28. Two tenants with different retention periods purge independently, verified across all four stores. |
| NFR-SEC-24 | `tenant-isolation.spec` shall be a release gate proving that a principal scoped to tenant A cannot read, write, retrieve, embed or cache against tenant B, exercised across all four stores and including forged-tenant payloads. | ADR-0002 required test; architecture §5 | MUST | The suite covers 5 operations × 4 stores plus the forgery cases, runs against a Compose environment with at least two provisioned tenants, and blocks release on any failure. A release with this suite unrun or failing is not a release. |
| NFR-SEC-26 | Every pipeline (`PipelineDesign`/`PipelineVersion`) shall be owned by exactly one tenant (`ownerTenantId`), and no pipeline, pipeline node, pipeline edge or pipeline trace field shall be readable, writable or referenceable by a principal of another tenant — including a node's `agentId`/`agentVersionPinId` reference, which shall resolve only to an agent owned by the same tenant. | Pipeline Designer delivery; ADR-0002 | MUST | A pipeline created in tenant A is absent from every list, canvas and history endpoint called as a principal of tenant B, and a direct id-guess request for it returns 404/403, not the record. Creating a `PipelineNode` that pins an `AgentVersion` belonging to another tenant is rejected server-side, mirroring the existing agent/knowledge-collection cross-tenant reference checks ([`agents.md`](./agents.md) FR-AGENT-13). |
