# 5.4 `agents` — registry, versions, lifecycle, wizard (B2, B3)

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-AGENT-01 | The system shall maintain an agent registry showing per agent the name, owning entity, current version, lifecycle status, bound channels and usage volume. | B2 | MUST | All six columns render for the four seeded agents. A Draft agent shows no channels and no usage. Status is one of `Draft`, `Published`, `Archived`. |
| FR-AGENT-02 | The system shall maintain an ordered version history per agent, each entry carrying a version identifier and a change summary, viewable inline from the registry. | B2 | MUST | The four seeded agents' histories match B2 exactly. Entries are ordered newest first and are immutable once written. |
| FR-AGENT-03 | The system shall clone an agent, producing a new `Draft` at version `v0.1` named `<original name> (copy)` with a history entry recording the source agent and version. | B2 actions | MUST | Cloning `SEWA & Utilities Billing Agent` yields `SEWA & Utilities Billing Agent (copy)`, status `Draft`, version `v0.1`, history entry "Cloned from SEWA & Utilities Billing Agent v1.4". The clone binds no channels and carries no usage. |
| FR-AGENT-04 | The system shall publish and unpublish an agent, changing its lifecycle status and its availability on bound channels. | B2 actions | MUST | Publishing makes the agent selectable by the router on its bound channels; unpublishing stops new routing to it while allowing in-flight turns to complete. Both actions are audited and require `Publish agents`. |
| FR-AGENT-05 | The system shall archive an agent, removing it from the active registry while retaining its versions, history and audit trail. | B2 actions | MUST | An archived agent is absent from the default registry list, cannot be routed to, and its version history remains retrievable. Archiving a `Published` agent unpublishes it first. |
| FR-AGENT-06 | The system shall roll back to any non-current version, setting it as current and prepending a history entry naming the version rolled back to. | B2 actions | MUST | Rolling back v1.4 → v1.2 makes v1.2 current and prepends "Rolled back to v1.2". No version record is deleted or edited. The action requires `Publish agents` and is audited. |
| FR-AGENT-07 | The system shall treat rollback and environment promotion as distinct operations: rollback changes which version is current within an environment; promotion moves a version between environments. | B2 `[rule]`; B14 tab 1 | MUST | Rolling back in Production does not alter UAT. Promoting UAT → Production does not change which version UAT holds. The two operations write distinguishable audit entries. |
| FR-AGENT-08 | The system shall provide a ten-step agent designer wizard in which any step is directly reachable without completing earlier steps, and all entered state shall persist across step navigation. | B3 structure | MUST | Jumping from step 1 to step 7 and back retains every field. A progress indicator reports completion. The final step's primary action reads *Publish agent*; all others read *Save & continue*. |
| FR-AGENT-09 | The wizard shall capture agent identity: name, owning entity, and description. | B3 step 1 | MUST | Owning entity is selectable only from tenants the author may administer. Name is unique per tenant. |
| FR-AGENT-10 | The wizard shall capture a system prompt and a tone selection from a defined set. | B3 step 2 | MUST | The prompt persists verbatim including whitespace. Tone is one of `Helpful`, `Formal`, `Concise` and is carried into the runtime prompt assembly. |
| FR-AGENT-11 | The wizard shall capture a primary model, a fallback model and a temperature as configuration on the agent version record, resolvable at runtime without a deployment. | B3 step 3; ADR-0004 rule 2 | MUST | Changing the primary model changes which model answers on the next turn, with no rebuild or restart. Temperature is validated to its permitted range. Model identifiers are opaque strings resolved through the `ChatModel` port. |
| FR-AGENT-12 | The system shall invoke the configured fallback model when the primary model errors or times out, and shall record the fallback on the turn trace. | ADR-0004 rule 4 | MUST | A test forcing a primary-model error produces an answer from the fallback and a trace entry naming both models and the trigger. The fallback path has its own test; an untested fallback is not a fallback. |
| FR-AGENT-13 | The wizard shall bind knowledge collections to the agent, offering only collections the agent's owning tenant may read. | B3 step 5 | MUST | The three seeded collections appear with the two seeded bindings checked. A collection belonging to another tenant is not offered and is rejected if submitted directly. |
| FR-AGENT-14 | The wizard shall bind flows to the agent, showing each flow's publication status. | B3 step 6 | MUST | `Pay utilities bill (Published)` and `Update account details (Draft)` render with status. Binding a Draft flow is permitted but is reported at publish as a warning. **[ASSUMPTION]** — the wireframe shows the status without stating a rule. |
| FR-AGENT-15 | The wizard shall set per-agent guardrail selections, subject to the locked-policy rules in `governance`. | B3 step 7; B12 | MUST | The three seeded guardrail rows render with their seeded values. Attempting to disable a locked policy from this step is refused server-side ([`governance.md`](./governance.md) FR-GOV-02). |
| FR-AGENT-16 | The wizard shall bind channels to the agent. | B3 step 8 | MUST | Web widget and WhatsApp are bound, Kiosk/IVR unbound, for the seeded agent. A channel that is `Disabled` at the channel level cannot be bound. |
| FR-AGENT-17 | The wizard shall provide a sandbox in which the agent under construction can be exercised end to end before publish, using the same runtime pipeline as production. | B3 step 9 | MUST | A sandbox turn produces a real routing decision, real retrieval and a real trace. Sandbox turns are marked as such and are excluded from analytics KPIs. Sandbox tool calls run against test connectors, never against a `Live` payment gateway. |
| FR-AGENT-18 | The wizard shall publish the agent to a selected environment, incrementing the version and recording a mandatory change summary. | B3 step 10 | MUST | Publishing v1.3 produces v1.4 with the entered summary as its history entry. An empty change summary blocks publish. Environment is selectable only from environments the principal may publish to. |
| FR-AGENT-19 | The system shall require the `Publish agents` permission for publish, unpublish, rollback and promotion, enforced server-side. | B9 tab 3; B3 step 10 | MUST | Each of the four operations returns 403 for an Agent Designer and succeeds for an Entity Admin. |
| FR-AGENT-20 | The system shall evaluate the evaluation publish gate before completing a publish and shall refuse the publish when the gate fails. | B13 tab 3; B3 step 10 | MUST | With the gate on and a failing suite, publish is refused with the message required by [`evaluation.md`](./evaluation.md) FR-EVAL-08. With the gate off, publish proceeds. The refusal is recorded. |
| FR-AGENT-21 | The system shall record per-agent usage volume per day, per channel, and shall expose it on the registry. | B2 | SHOULD | Usage counts reconcile with the conversation records for the same period and tenant. Sandbox turns are excluded. |
