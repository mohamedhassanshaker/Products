# 5.14 `evaluation` — golden sets, regression runs, publish gate (B13)

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-EVAL-01 | The system shall maintain golden sets recording name, case count, owning entity and last score. | B13 tab 1 | MUST | The four seeded sets render with all four fields. A set belongs to one tenant and cannot be run against another tenant's agent. |
| FR-EVAL-02 | The system shall run a golden set on demand, producing a fresh score recorded against the agent version tested. | B13 tab 1 | MUST | Running a set produces a new score and a new run record naming the set, the agent, the version and the timestamp. The previous score is retained in history. |
| FR-EVAL-03 | The system shall add a conversation to a golden set from the conversation explorer, incrementing the set's case count, and shall not add the same conversation to the same set twice. | B13 tab 1; B1 tab 2; [`cross-module.md`](./cross-module.md) | MUST | Adding increments the count by exactly one and the action becomes unavailable for that conversation and set, with confirmation text. A duplicate submission through the API is rejected. |
| FR-EVAL-04 | The system shall edit the cases within a golden set, including adding, amending and removing a case with its expected outcome. | B13 tab 1 | SHOULD | Case edits persist and change subsequent scoring. The wireframe marks this control static; it is required in the product. |
| FR-EVAL-05 | The system shall record regression runs holding the agent, version, set, accuracy, groundedness, tool accuracy and a pass/fail result. | B13 tab 2 | MUST | The three seeded runs render with all seven fields. The result is derived from the thresholds in FR-EVAL-07, not stored independently of them. |
| FR-EVAL-06 | The system shall run all suites on demand, producing one run record per agent/set pairing. | B13 tab 2 | MUST | A run-all produces the expected number of run records and prepends them to the history. Existing records are never overwritten. |
| FR-EVAL-07 | The system shall configure a publish gate comprising: block publish when a suite fails; a minimum accuracy threshold defaulting to 85%; a minimum groundedness threshold defaulting to 80%; a requirement that the red-team set scores 100%; and a requirement blocking publish when a bound locale is below 100% translated. | B13 tab 3 | MUST | All five settings persist with the seeded defaults. Each is independently effective — disabling one does not disable the others. |
| FR-EVAL-08 | The system shall state, when the gate blocks a publish, the agent and version blocked, the failing set, its score and the threshold it missed. | B13 tab 3 `[rule]` | MUST | Blocking the General FAQ Agent v3.0 produces a message naming the agent, the version, the Arabic language parity set, its 71% score and the 85% accuracy floor. A block message that names only the fact of blocking fails this requirement. |
| FR-EVAL-09 | The system shall block publish of an agent bound to a locale below 100% translated, naming the locale and its translation percentage in the block message. | B13 tab 3; B10 tab 5 `[rule]` | MUST | An agent bound to Arabic at 82% is blocked with a message naming Arabic and 82%. Reaching 100% permits the publish. This gate is independent of the accuracy gate — both can block the same publish for different reasons (see [`risks.md`](./risks.md) RISK-007). |
| FR-EVAL-10 | The system shall permit publish regardless of test results when the gate is disabled, and shall state that consequence on the configuration surface. | B13 tab 3 | MUST | With the gate off, the failing agent publishes and the surface states that any agent can be published regardless of test results. Disabling the gate is audited. |
| FR-EVAL-11 | The system shall evaluate the gate at publish time against the most recent run for the exact agent version being published, and shall block when no run exists for that version. | B13 tab 3 | MUST | Publishing a version with no run is blocked with a message naming the absence. A run against a different version does not satisfy the gate. |
| FR-EVAL-12 | The system shall block publish when the red-team set scores below 100%, irrespective of accuracy and groundedness scores. | B13 tab 3 | MUST | A red-team score of 96% blocks publish even with accuracy at 99% and groundedness at 95%, and the message names the red-team set and its score. |
| FR-EVAL-13 | The system shall audit every change to the publish gate configuration, every gate-blocked publish attempt and every publish permitted with the gate disabled. | B14 tab 2 | MUST | Each of the three events produces an audit entry. A gate-disabled publish is distinguishable in the audit log from a gate-passed publish. |
| FR-EVAL-14 | Adding a conversation to a golden set from the command centre shall increment that set's case count and create a case referencing the source conversation, with the two sides always consistent. | `analytics` → `evaluation`; B1 → B13 | MUST | Add a transcript to *Billing core journeys*: the count increases by one and the new case names the conversation. The set's stored count equals the number of its cases, asserted after a batch of additions. *(Cross-module invariant; also listed in [`cross-module.md`](./cross-module.md).)* |
| FR-EVAL-15 | The publish gate shall read locale translation completeness from the channels module's live figure, and shall block a bound agent naming that locale and that percentage, so the two screens can never disagree about Arabic readiness. | `channels` → `evaluation`; B10 tab 5 → B13 tab 3 | MUST | With Arabic at 82%, the gate blocks a bound agent naming Arabic and 82%. Raise Arabic to 100%: the gate stops blocking on that ground without any evaluation-side edit. The gate holds no copied percentage. *(Cross-module invariant; also listed in [`cross-module.md`](./cross-module.md).)* |
