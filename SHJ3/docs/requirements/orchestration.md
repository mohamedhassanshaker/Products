# 5.5 `orchestration` — router, execution modes, traces, pipeline designer (B4)

Runs across both runtimes: configuration and canvas in `shj3-web`, execution in `shj3-ai`.

## 5.5.1 Baseline — three fixed execution modes (B4)

Satisfies brief requirement R5's original scope. This is the release-1 baseline and remains the fallback behaviour for any tenant that has not activated a pipeline (§5.5.2).

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-ORCH-01 | The system shall process every citizen turn through the pipeline *guardrail pre-check → route → execute → merge → guardrail post-check → stream and persist*. | B4 diagram; architecture §7 | MUST | A turn that skips any stage is impossible: the stages are structural, not conditional on configuration. Each stage is visible on the persisted trace. |
| FR-ORCH-02 | The system shall support three execution modes — sequential, parallel, and supervisor–worker — selectable as configuration. | B4 modes | MUST | All three modes are selectable and produce the distinct behaviours in FR-ORCH-03 to FR-ORCH-05. The active mode is recorded on every trace. |
| FR-ORCH-03 | In sequential mode the system shall run one selected agent to completion, then hand to a secondary agent if required, and merge replies in invocation order. | B4 modes | MUST | For "Pay SEWA bills": the trace shows the router selecting the billing agent, the billing agent calling `get_bill_status()`, a hand to the knowledge agent, then a merge preserving order. |
| FR-ORCH-04 | In parallel mode the system shall fan out to multiple agents within one turn and shall resolve overlapping content at merge. | B4 modes | MUST | The trace shows concurrent invocation and a single merged reply with no duplicated statement. Turn latency is bounded by the slowest agent, not the sum. |
| FR-ORCH-05 | In supervisor–worker mode the system shall produce an explicit plan of sub-tasks, delegate each to a worker agent, and review the aggregate before responding. | B4 modes | MUST | The trace shows the plan (fetch bill → check eligibility → prepare payment link), one delegation per sub-task, and a supervisor review step before the reply is emitted. |
| FR-ORCH-06 | The system shall configure the routing strategy and the scope of agents the router may select from. | B4 configuration | MUST | The selection scope restricts the router to the configured agent set; an agent outside the scope is never selected. Scope cannot include agents from another tenant. |
| FR-ORCH-07 | The system shall enforce a maximum hop count and a loop ceiling per turn, terminating the turn with the configured fallback behaviour when either is reached. | B4 configuration | MUST | A deliberately looping configuration terminates at the ceiling rather than running unbounded, records the reason on the trace, and returns the fallback response. |
| FR-ORCH-08 | The system shall record tokens and cost for every model call against tenant, agent and conversation, and shall enforce a configurable per-turn cost ceiling using those figures. | B4 configuration; ADR-0004 rule 5 | MUST | Every model call yields a cost record. A turn exceeding the ceiling terminates with the fallback and a trace entry naming the ceiling and the accumulated cost. Records are queryable per tenant, agent and conversation. |
| FR-ORCH-09 | The system shall apply a configured conflict-resolution and response-merge policy when two agents return contradicting or overlapping content. | B4 configuration | MUST | Given two contradicting agent replies, the merged output follows the configured policy deterministically and the discarded content is recorded on the trace. |
| FR-ORCH-10 | The system shall route to a configured fallback agent when the router cannot select an agent above its confidence floor. | B4 configuration | MUST | A prompt matching no agent is handled by the fallback agent, and the trace records the routing failure and the fallback selection. |
| FR-ORCH-11 | The system shall persist one trace per turn, containing the routing decision with numeric confidence, the execution mode, every tool call with arguments and outcome, every retrieval performed, the merge decision, and both guardrail verdicts. | A2; B4; architecture §7 | MUST | The seeded journey's step-2 trace records `router → billing_agent (confidence 0.94)`. Traces are retrievable per conversation and are written by `shj3-ai` (one of its three permitted write groups, ADR-0005 rule 5). |
| FR-ORCH-12 | The system shall report per-mode latency and token cost so the mode's cost/latency trade-off is measurable rather than asserted. | B4 `[rule]` | SHOULD | Running the same prompt in all three modes yields three comparable latency and cost figures. Parallel shows the lowest latency; supervisor–worker the highest token cost. |
| FR-ORCH-13 | The system shall re-open routing when a free-text escape fires, re-evaluating the next prompt against the full agent scope while preserving conversation context. | A2 step 4; B7 condition node | MUST | After "i have another inquiry" the trace shows `flow escape triggered → context preserved` followed by a fresh routing decision. The prior flow state remains resumable ([`conversation.md`](./conversation.md) FR-CONV-15). |
| FR-ORCH-14 | The system shall execute the guardrail pre-check and post-check as non-optional pipeline stages that no role and no per-agent configuration can disable. | architecture §7; B12 tab 1 `[rule]` | MUST | No configuration value removes either stage. A test attempting to disable them via API, per-agent override and direct database edit leaves the stages running. |

## 5.5.2 Pipeline Designer — arbitrary, versioned, loop-capable agent graph

**Delivery-added.** Beyond the original wireframe brief: a real drag-and-drop canvas under `/orchestrator/pipelines` that replaces the single flat `executionMode` enum with an arbitrary agent graph, per tenant, per named and versioned pipeline. §5.5.1's three fixed modes are not removed — they remain the behaviour for any tenant with no active pipeline (FR-ORCH-25) and are the documented Phase-1 fallback (`_legacy_single_agent` in `apps/ai`'s `process_turn.py`). This sub-module generalises brief requirement R5 rather than replacing it: "multiple agents can be assigned to one prompt" is now expressible as any graph shape, not only the three named ones.

Every requirement below was verified directly against the shipped code (schema, constraints, Python domain module, web module, canvas components, routes) as part of writing this document, not transcribed from the delivery plan.

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-ORCH-15 | The system shall maintain multiple, named, versioned pipelines per tenant (`PipelineDesign` → `PipelineVersion`), following the same `Draft → Published → Archived` lifecycle, fork-a-draft-off-current-Published, and rollback-capable pattern already established for `Agent`/`AgentVersion` and `Flow`/`FlowVersion`. | Pipeline Designer delivery | MUST | `PipelineDesign`/`PipelineVersion`/`PipelineNode`/`PipelineEdge`/`PipelineVersionHistoryEntry` exist in `prisma/tenant/schema.prisma`. A `PipelineDesign.slug` is unique among non-deleted designs per tenant. Forking a Draft off a Published version reuses an existing Draft rather than creating a second one on every editor page load — a real, live-reproduced bug fixed in this delivery (`get-or-create-draft-pipeline-version.ts`, regression-tested). |
| FR-ORCH-16 | The system shall model a pipeline as an arbitrary graph of nodes (`Start`, `Agent`, `Supervisor`, `Response`) and edges (`Sequential`, `Parallel`, `LoopBack`), where any node may connect to any other and a real cycle is representable only through an edge explicitly marked `LoopBack`. | Pipeline Designer delivery | MUST | `TR_PipelineEdges_homogeneousFanOut` enforces that a node's non-loop outgoing edges are either exactly one `Sequential` or two-or-more, all `Parallel` — a 1-way "parallel" edge and an orderless 2-way "sequential" fan-out are both unrepresentable. `CK_PipelineEdges_selfLoopOnlyLoopBack` permits a self-edge only when it is a loop-back. |
| FR-ORCH-17 | A `LoopBack` edge shall carry a mandatory `maxIterations` (a hard backstop, bounded 1–20) and may optionally carry a `conditionExpression`, evaluated on every pass; the bound is checked first and unconditionally, and a false condition exits the loop even under the bound. | Pipeline Designer delivery | MUST | `CK_PipelineEdges_loopFields` requires `maxIterations` if and only if `kind = 'LoopBack'`. `CK_PipelineEdges_maxIterationsBounded` enforces the 1–20 range. `decide_loop_back()` (`apps/ai/src/shj3_ai/domain/pipeline.py`) checks `taken >= maxIterations` first, before consulting any condition; on a condition evaluation error the loop exits rather than continuing (fail closed). |
| FR-ORCH-18 | A loop-back condition shall be expressed in a small, whitelisted comparison grammar — `and`/`or` of `field operator literal` comparisons over a fixed field table, with no arbitrary code execution — validated at save time against the version's real node keys and against per-field type rules. | Pipeline Designer delivery | MUST | `apps/ai/src/shj3_ai/domain/condition_expr.py` implements the grammar: operators `< <= > >= == != contains`; whitelisted fields `iteration`, `hopCount`, `groundingConfidence`, `costTokens`, `costMicroAed`, `branchCostTokens`, `degraded`, `usedFallbackModel`, `lastReply.*`, and the templated `node.<key>.*` family; limits of 500 characters and 8 comparisons. A condition naming an unknown field is rejected at validation (`POST /v1/orchestration/pipelines/validate-condition`), never evaluated at runtime. A field that resolves to nothing at run time evaluates the comparison `False` — the conservative direction, never extending a loop on missing data. |
| FR-ORCH-19 | The system shall reject publishing a pipeline version whose graph is not a single connected structure with exactly one entry (its own `Start` node), at least one `Response` node, no orphaned node, no reference to a Draft agent or agent version, and no cycle through non-loop edges other than a `LoopBack` edge that targets an ancestor of its own source. | Pipeline Designer delivery | MUST | `TR_PipelineVersions_publishGraphValid` (a database trigger, `AFTER INSERT, UPDATE`, gated on `status = 'Published'`) enforces every clause above. The equivalent client-side analyzer (`analyzePipelineGraph`, `apps/web`'s `domain/pipeline-graph.ts`) and the AI-side `validate_definition` (`apps/ai/src/shj3_ai/domain/pipeline.py`) implement the identical rule set, so a client-rejected graph and a server-rejected graph never disagree. Verified live: publishing "test" (a lone, disconnected Start node with no Response node) is blocked, and the findings panel names both violated rules verbatim. |
| FR-ORCH-20 | A pipeline version shall carry its own hop ceiling (`maxTotalHops`, 1–50) and cost ceilings (`costCeilingTokens`, `costCeilingMicroAed`); the effective ceiling enforced at run time shall be the minimum of the tenant-wide `RouterConfigs` ceiling and the active pipeline version's own ceiling, so a pipeline can only tighten the tenant's cap, never loosen it. | Pipeline Designer delivery | MUST | `CK_PipelineVersions_ceilings` enforces `maxTotalHops BETWEEN 1 AND 50` (widened from the legacy 1–10 range; `CK_OrchestrationTraces_hops` is widened to match, since a looped turn beyond 10 invocations must not fail the trace insert after money has already been spent). `ExecutePipeline.execute()` computes `min(router, pipeline)` and terminates with the configured fallback when either figure is reached, recording the reason on the trace — the same mechanism FR-ORCH-07/08 already established, now reused rather than reimplemented. |
| FR-ORCH-21 | Each node shall independently configure its input-context mode (`UserTurnOnly`, `UpstreamRepliesFull`, `UpstreamRepliesSummary`), its error policy (`FailTurn`, `SkipNode`, `RouteToFallbackAgent`), whether it is the owning entity for the turn, and optional per-node cost/timeout overrides; a merge-policy or conflict-resolution override shall be legal only on a node with two or more real inbound edges. | Pipeline Designer delivery | MUST | A `SkipNode` failure marks its outgoing edges satisfied so a downstream join is never left waiting indefinitely — directly unit-tested (`apps/ai/tests/application/test_execute_pipeline.py`). Submitting a merge/conflict override on a node with fewer than two inbound edges is rejected server-side. |
| FR-ORCH-22 | The pipeline execution engine shall resolve a "ready set" of nodes whose forward inputs are all satisfied, running it sequentially (one `await`) when it has one node and concurrently (`asyncio.gather`, emitting a `FanOut` trace step) when it has more than one, and shall reuse the existing, already-tested `merge_replies()` unchanged at any join of two or more satisfied inputs. | Pipeline Designer delivery | MUST | `ExecutePipeline.execute()` (`apps/ai/src/shj3_ai/application/execute_pipeline.py`) implements this; `next_ready_set()` (`domain/pipeline.py`) sorts ready nodes deterministically by incoming-edge ordinal then key, never by completion order, so identical inputs always produce an identical trace shape. A 2-way parallel fan-out with a real join is covered by `apps/ai/tests/application/test_execute_pipeline.py`. |
| FR-ORCH-23 | The system shall provide a graphical, drag-and-drop canvas for authoring a pipeline's nodes and edges, in which every drag gesture (adding a node from the palette, repositioning a node) has a stated non-drag equivalent, and below the mobile breakpoint drag is omitted entirely in favour of the accessible click/keyboard path. | Pipeline Designer delivery; design-system.md's drag-and-drop rule | MUST | `components/patterns/pipeline-canvas/` (`pipeline-canvas-graph.tsx`, `pipeline-canvas-surface.tsx`, `pipeline-graph-node.tsx`, `pipeline-graph-edge.tsx`, `pipeline-agent-palette.tsx`, `pipeline-canvas-outline-view.tsx`, `pipeline-node-inspector.tsx`) implement this. A palette entry is both `draggable` and a plain `onClick`, one code path serving both gestures. Verified live in the running Docker stack: a real 1-node and a real 3-node pipeline both render correctly on the canvas after the container-height layout defect found during this delivery was fixed (see below). |
| FR-ORCH-24 | The editor shall run the shared graph analyzer on every change, present every blocking and advisory finding in a findings panel, disable Publish while any blocking finding exists, and render a server-rejected publish through the identical panel and message text as a client-side finding. | Pipeline Designer delivery | MUST | Verified live against the real dev stack: the "test" pipeline (one disconnected `Start` node, no `Response` node) shows "Fix 2 issues to publish" with Publish disabled, and the two findings quoted verbatim are "The pipeline needs at least one Response node." and "This node is not connected to the rest of the pipeline." |
| FR-ORCH-25 | The system shall let a tenant name at most one `Published` pipeline version as active (`RouterConfig.activePipelineVersionId`); while unset, the tenant's turns continue to run through the three legacy execution modes (§5.5.1) via an explicit `_legacy_single_agent` fallback path — activating a pipeline is a deliberate, separate, audited action, never an implicit side effect of publishing it. | Pipeline Designer delivery | MUST | `RouterConfig.activePipelineVersionId` is a nullable FK to `PipelineVersion`. `process_turn.py` branches on this column: null routes to `_legacy_single_agent`, set routes to `ExecutePipeline.execute()`. Setting it requires the named version to be `Published` (`TR_RouterConfigs_activePipelinePublished`). |
| FR-ORCH-26 | While a tenant has an active pipeline, the legacy execution-mode controls on `/orchestrator` (execution mode, agent selection scope) shall render disabled under an explanatory notice pointing at the pipeline editor, so the two configuration surfaces can never simultaneously claim authority over the same turn. | Pipeline Designer delivery | MUST | `execution-mode-panel.tsx` accepts an `activePipeline` prop; when present, the mode and scope controls render `disabled` under an `InlineAlert`. Clearing the active pipeline re-enables them. `RouterConfigs`' ceiling fields remain live regardless (FR-ORCH-20), since they are pipeline-orthogonal tenant-wide rails. |
| FR-ORCH-27 | Every pipeline lifecycle event — `Created`, `Cloned`, `Published`, `Unpublished`, `RolledBack`, `Activated`, `Archived` — shall be recorded as an append-only history entry naming the actor and the timestamp, mirroring the existing `AgentVersionHistoryEntry` mechanism exactly, with `Activated` as the one event kind this delivery adds. | Pipeline Designer delivery | MUST | `PipelineVersionHistoryEntry` exists with the seven `kind` values above. Activating a pipeline writes exactly one `Activated` entry naming the actor. |
| FR-ORCH-28 | The executed graph of a pipeline turn — its nodes, its edges, their topological columns, their parallel/loop lanes, and every loop decision taken — shall be fully reconstructible from `OrchestrationTraceSteps` alone, with no read of the (potentially since-archived-and-deleted) `PipelineNode`/`PipelineEdge` rows. | Pipeline Designer delivery | MUST | `OrchestrationTrace` gains `pipelineVersionId`, `pipelineDesignId`, a frozen `pipelineLabel` string (e.g. `"v1.2"`, deliberately duplicated text rather than a join, so the trace stays legible after the version is archived), `terminalNodeKey`, `branchCount`, `loopIterationsTotal`. `OrchestrationTraceStep` gains frozen copies `pipelineNodeKey`, `fromNodeKey`, `edgeKind`, plus `branchId` (a dotted string, e.g. `"0.1.0"`), `loopIteration`, `depth`, and two new step kinds, `FanOut` and `LoopBack`. `execution_mode` gains the value `'Pipeline'` alongside the three legacy values. |
| FR-ORCH-29 | The system shall provide a one-time, idempotent, per-tenant backfill that synthesizes an equivalent `v1.0` Published pipeline from each tenant's current flat `RouterConfigs.executionMode`, without activating it, so no tenant's live turn behaviour changes as a side effect of the migration landing. | Pipeline Designer delivery | MUST | `scripts/backfill-pipeline-from-router-config.ts`. Running it a second time against an already-backfilled tenant reports `skipped-already-backfilled` rather than creating a duplicate design. Every created node carries a real, distinct canvas position — a real defect (all nodes landing at `(0,0)`, collapsing `fitView`'s bounding box and making the canvas appear empty) found and fixed live against real tenant data during this delivery. `RouterConfig.activePipelineVersionId` is left `null` by the backfill; a tenant only sees pipeline-governed behaviour after a deliberate, separate activation. |
| FR-ORCH-30 | The Pipeline Designer shall require no new permission: the existing `orchestration:manage` permission (already seeded for `Super Admin` and `Entity Admin`) shall gate every pipeline action — list, create, edit the canvas, publish, activate, roll back, view history, validate. | Pipeline Designer delivery | MUST | Every Server Action in `orchestrator/pipelines/actions.ts` and both route-level `page.tsx` files call `requirePermission(principal, "orchestration:manage", ...)`. A principal lacking it receives 403 on every pipeline route, matching [`iam.md`](./iam.md)'s deny-by-default rule (FR-IAM-12). |

### Known gap — Pipeline Designer end-to-end test coverage

The pure domain logic on both sides is unit-tested (`apps/ai/tests/domain/test_pipeline.py`, `test_condition_expr.py`, `apps/ai/tests/application/test_execute_pipeline.py` on the Python side; `apps/web`'s `.test.ts` files alongside every port, use-case and canvas component on the TypeScript side — 289 test files, 2,282 tests passing as of this delivery). **No Playwright end-to-end spec exercises the Pipeline Designer** — there is no `e2e/**/pipeline*.spec.ts` and no `e2e/**/orchestrator*.spec.ts` covering the drag-and-drop canvas, the publish flow, or the activation flow through a real browser against the real running stack, despite the pre-existing e2e infrastructure (`e2e/journeys/*`, `e2e/backoffice/*`, session-minting via `scripts/mint-e2e-sessions.ts`) being reusable for exactly this. Four real runtime defects in this feature (a stale generated Prisma client, a corrupted `.next` build cache, overlapping canvas node positions, and a canvas-collapsing CSS layout bug) were instead found by the user testing manually in a browser and fixed reactively. Per this document's own Phase D rule ("a requirement with no passing test is an incomplete requirement"), FR-ORCH-15 through FR-ORCH-30 above are implemented and manually/live-verified but not yet covered by an automated E2E suite. Tracked as **RISK-026** in [`risks.md`](./risks.md).
