# 5.2 `iam` — users, teams, roles, sessions (B9)

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-IAM-01 | The system shall maintain user records with name, email, team, role and status, where status is one of `Invited`, `Active`, `Suspended`. | B9 tab 1 | MUST | All three statuses render with a text label, never colour alone. Transitions are restricted to the paths in FR-IAM-02 and FR-IAM-03. |
| FR-IAM-02 | The system shall create invited users in `Invited` status and shall promote them to `Active` only on invite acceptance with credential enrolment. | B9 tab 1; ADR-0006 rule 4 | MUST | A newly invited user cannot authenticate. After acceptance the status is `Active` and a credential exists. Invite tokens are single-use and expire. |
| FR-IAM-03 | The system shall suspend and reactivate users, and suspension shall terminate all of that user's sessions immediately rather than at expiry. | B9 tab 1; ADR-0006 consequences | MUST | Suspend a user holding an active session; the next request on that session returns 401. Reactivation does not restore the old session. |
| FR-IAM-04 | The system shall remove a user while retaining their identity references on historical audit and transcript records. | B9 tab 1; B14 tab 2 | MUST | After removal the user cannot authenticate and is absent from lists; existing audit entries still name them and are not mutated. |
| FR-IAM-05 | The system shall edit a user's name, email, team assignment and role assignment. | B9 tab 1 | MUST | Each field persists. Email is unique per tenant. A role change takes effect on the user's next authorisation check without re-login. |
| FR-IAM-06 | The system shall maintain teams, each carrying an entity scope, where the `Platform` team scopes to all entities. | B9 tab 2 | MUST | Four teams seeded with the scopes in B9 tab 2. A team's entity scope constrains what its members may read and cannot be set to a tenant the editor may not administer. |
| FR-IAM-07 | The system shall derive team membership from user team assignment rather than storing it as a second, independently writable relation. | B9 tab 2 | MUST | There is exactly one write path for membership. Reassigning a user changes the team view with no second write. |
| FR-IAM-08 | The system shall create teams with a name and an entity scope. | B9 tab 2 | MUST | A new team appears with zero members and its stated scope. Name is unique per tenant. |
| FR-IAM-09 | The system shall maintain a role/permission matrix of at least the seven seeded roles against the eight seeded permissions, with every cell independently settable. | B9 tab 3 | MUST | The seeded matrix matches B9 tab 3 cell for cell. Toggling a cell changes effective authorisation for holders of that role on their next check. |
| FR-IAM-10 | The system shall create custom roles, which shall start with all permissions denied. | B9 tab 3 | MUST | A newly created role grants nothing; a user holding only that role is denied every gated endpoint until a permission is granted. |
| FR-IAM-11 | The system shall separate authoring from release: `Manage agents` shall permit creating and editing an agent, and `Publish agents` shall be required to publish, unpublish or promote one. | B9 tab 3 `[rule]` | MUST | An Agent Designer completes the wizard through step 9 and is denied server-side at publish, with an error naming the missing permission. An Entity Admin publishes the same draft successfully. |
| FR-IAM-12 | The system shall evaluate authorisation deny-by-default against the permission set on the authenticated `Principal`, in the server-side inbound adapter, and shall never depend on a role-name comparison or on a client-side check. | ADR-0006 rule 7; architecture §10 | MUST | Every gated route has a server-side check. No authorisation decision compares a role-name string. Calling each gated endpoint with an under-privileged session returns 403 even where the UI would have hidden the control. |
| FR-IAM-13 | The system shall authenticate staff with email and password hashed using Argon2id, shall require TOTP for every role holding `Publish agents` or `Manage users & teams`, and shall apply rate limiting with progressive backoff plus account lockout on repeated failure. | ADR-0006 rule 4 | MUST | Password verification uses Argon2id with documented parameters. A Super Admin or Entity Admin cannot complete sign-in without TOTP. Backoff and lockout thresholds are configurable and every lockout is audited. |
| FR-IAM-14 | The system shall hold staff sessions server-side in Redis keyed by an opaque identifier, and shall not issue a client-readable token carrying claims the application interprets. | ADR-0006 rule 2 | MUST | The session cookie value is opaque and carries no encoded claims. Deleting the server-side session revokes access on the next request. |
| FR-IAM-15 | The system shall authenticate through an `IdentityProvider` port whose adapter is selected by environment configuration, and no feature module shall reference a credential, token, cookie or identity-provider claim. | ADR-0006 rules 1, 3 | MUST | A search across feature modules returns no reference to a password, JWT, cookie or OIDC claim. Swapping the configured adapter changes no feature-module file. |
| FR-IAM-16 | The system shall store staff credentials in a table owned solely by the local authentication adapter; the user record shall carry no credential column. | ADR-0006 rule 3 | MUST | The Prisma schema shows no credential column on the user model. Dropping the credential table breaks only the local adapter. |
| FR-IAM-17 | The system shall write an audit entry for every user creation, removal, suspension, reactivation, role grant, role revocation, team change and permission-matrix change. | B14 tab 2 | MUST | Each of the eight operations produces exactly one audit entry naming actor, subject, before and after value, and environment. |
| FR-IAM-18 | Team membership shall be a single derived projection of user team assignment, so a reassignment in the users view is immediately reflected in the teams view with no second write. | `iam`; B9 tab 1 → tab 2 | MUST | Reassign a user from Libraries to Customs; both views agree on the next read. A test asserts no writable membership relation exists independently of the user record. *(Cross-module invariant; also listed in [`cross-module.md`](./cross-module.md).)* |
