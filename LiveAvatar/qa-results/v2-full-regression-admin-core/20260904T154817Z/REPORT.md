## 2. A note on a defect found, and on this pass own tooling defect (read before the matrix)

**A real backend defect was found and root-caused, then found already fixed.** When first booting the public API (`node dist/main.js`) against a freshly-built `dist/`, NestJS failed to start with `UnknownDependenciesException`: `HitlSlaSweepProcessor` (in `JobsModule`) could not resolve `HITL_DEFERRED_FOLLOWUP_QUEUE_PORT`. Root cause, read directly from source: `apps/api/src/modules/hitl/hitl.module.ts` exports array listed `HITL_GATE_REPOSITORY`, `HITL_DECISION_REPOSITORY`, `REVIEWER_GROUP_REPOSITORY`, `CreateHitlDecisionUseCase`, `GetHitlDecisionUseCase` — but not `HITL_DEFERRED_FOLLOWUP_QUEUE_PORT`, which `JobsModule` needs for its own `HitlSlaSweepProcessor` provider. **This crashed the entire public API process** (every `/api/*` route — tenants, sessions, dashboard, GPU, alerts, providers, deployment-config — all of it), not just the HITL surface. Before a workaround was applied, the shared source (this is a repo checkout shared with two other concurrent QA passes) was found already corrected — `hitl.module.ts` now lists `HITL_DEFERRED_FOLLOWUP_QUEUE_PORT` in exports, and a fresh build boots cleanly. This is reported because it is a genuine, independently-diagnosed defect that existed in the tree during this pass, even though it was not this pass own fix and is not present in the final state tested.

**This pass own test-tooling defect cost significant time and left 4 screens worth of live-browser evidence incomplete.** The first full walkthrough attempt used `page.getByLabel("Password")` to fill the login form; Playwright getByLabel does *substring*, not exact, matching by default, so it matched **two** elements — the password `<input>` and the "Show password" visibility-toggle button (`aria-label="Show password"` contains "password"). This is a strict-mode violation that threw on every `.fill()` call, so login never completed in that run, and every subsequent `page.goto()` to a protected route was silently bounced back to `/login` by the app own (correctly-functioning) auth guard — 20+ "different" screenshots that were in fact all the same login page. This was root-caused and fixed (`exact: true` on the ambiguous locators) and re-run. The **second** run fixed login but hit a second, same-shape bug: the shared `TenantSelectComponent` autocomplete open listbox panel and its input both carry the accessible name "Tenant", so `getByLabel("Tenant", { exact: true })` intermittently matched two elements once a prior selection had already opened the panel once in the same page lifetime. That blocked the tenant-scoped navigation into Sessions, tenant-scoped Alerts, the Reviewer console, and the Residency-to-Builder-privacy redirect specifically (every screen reached via that shared picker, later in the run). Under an explicit instruction to stop iterating and report now, this was **not** fixed with a third run. Every item below affected by this is marked "not completed" rather than PASS or FAIL.

## 4. Defects and findings, ordered by severity

### F-1 (High, but already resolved in the tree, informational) — HitlModule was missing an export, crashing the entire public API
See Section 2 for the full root cause. At the time this pass began, `node dist/main.js` could not start at all — a total outage of every `/api/*` route, not scoped to HITL. By the time a workaround was needed, the shared source already had the fix (`HITL_DEFERRED_FOLLOWUP_QUEUE_PORT` added to HitlModule exports). Recommend: add a boot-smoke-test (does AppModule compile and start) to CI, since this class of DI-wiring break is invisible to unit tests that mock the DI container.

### F-2 (Moderate, scope/process risk, not a product defect) — Four in-scope UI surfaces not verified this pass
Sessions list/detail, the tenant-scoped Alerts screen (with all 5 alert types), the Reviewer console live decision queue, and the Residency-picker redirect into the Builder were not captured via the browser due to a test-script selector-ambiguity bug in the shared TenantSelectComponent autocomplete (see Section 2), not a confirmed product issue. The underlying data and API contracts for all four were independently verified as correct at the HTTP level. **This is a real gap in this QA pass own coverage** and should be closed with a follow-up UI pass before these areas are signed off — it is listed as a defect against this pass own process, not against the product.

### F-3 (Low) — Provider-credential probe UI: in-flight "Testing..." state was the last captured frame for the live-added credential
Not a defect — the probe request was genuinely in flight and the UI was correctly reflecting that transient state ("Testing...") — but this pass did not wait long enough to capture its resolved state for that one specific credential (the other 5 credentials resolved states, captured moments earlier in the same tenant, are unaffected and shown correctly mixed Healthy/Unreachable).

No other defects — confirmed or suspected — were observed in any screen this pass actually reached. Every previously-reported defect from earlier phases that this pass screens touch (dashboard category-label casing, GPU role labels, no scale controls, phone dashboard layout) was re-confirmed as still fixed.

## 6. Environment notes

- `postgres:16-alpine` does not ship the vector extension needed by the `20260902202319_knowledge_rag` migration; switched to `pgvector/pgvector:pg16` for qa-v2-core-pg.
- `prisma migrate reset` was attempted once to get a clean slate after a slug collision on a re-run; **Prisma own AI-safety guard correctly refused it** (it stated that as an AI agent, this action is forbidden without explicit user consent). This was respected — no override was attempted, no consent was fabricated — and the seed script was made idempotent instead (safe to re-run, reuses existing tenants/credentials/gates by natural key rather than erroring).
- This repo checkout is shared with two other concurrent QA passes (a Builder-tab pass and a conversation-app pass) working in the same working directory at the same time. One concrete effect was observed: apps/api/dist was rebuilt by another process mid-pass (caught mid-write once, retried successfully), and the HITL export fix in Section 2 most likely landed from that concurrent work, not from this pass. To avoid depending on a shared, moving dist/, this pass own backend processes were run from a private snapshot copy (apps/api/dist-qa/, deleted at teardown) taken immediately after this pass own build.
- Backend/frontend processes and Docker containers used exclusively by this pass (qa-v2-core-pg, qa-v2-core-redis, qa-v2-core-lk, the two dist-qa node processes, and the ng serve instance on port 25695) have all been **torn down**. The other agent own qa-v2-builder-* containers and its ng serve on port 25710 were left untouched and were not touched at any point.
