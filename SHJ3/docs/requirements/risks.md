# 9. Risks and open questions

Each risk states impact, likelihood, mitigation, and the decision needed and from whom. IDs are permanent.

| ID | Risk | Sev | Impact | Likelihood | Mitigation | Decision needed |
|---|---|---|---|---|---|---|
| **RISK-001** | Embeddings (OpenAI `text-embedding-3-large`), reranking (Cohere `rerank-v3.5`) and chat (OpenRouter) transmit citizen text outside the UAE, conflicting with the `UAE — Sharjah data centre` residency default the product itself exposes in B14 tab 4. | **High** | A governance conflict inside the product's own configuration surface: the system would report a residency posture it does not hold. Potential regulatory exposure on real citizen data; [`governance.md`](./governance.md) FR-GOV-26 makes the conflict visible rather than hidden, which is correct but not a resolution. | High — it is already true of the selected stack (ADR-0004). | All three capabilities sit behind ports (`ChatModel`, `EmbeddingProvider`, `Reranker`), so a swap to self-hosted **BGE-M3 + `bge-reranker-v2-m3`** is a one-adapter change. A spike comparing the two on the *Arabic language parity* golden set is the deciding measurement. Until resolved, no production deployment may carry real citizen data. | **A signed residency exception from the Sharjah data-protection authority and the product owner, or approval to fund the self-hosted GPU inference path.** Owner: product owner with the entity's data-protection function. Must be resolved before the first production deployment carrying real citizen data. |
| **RISK-002** | No CI/CD was selected, so nothing enforces lint, typecheck, boundary checks, the Prisma→SQLAlchemy drift check or tests on a shared branch. | **Medium-high** | The project's own non-negotiable quality rule is waived. A commit failing any gate can land. The drift check is the sole protection against the two-migration-tool corruption scenario, and `--no-verify` bypasses it. Phase D's requirement that E2E run in CI with no manual steps cannot be met. | High that a gate is bypassed once a second person commits; low while there is one committer. | Pre-commit hooks are mandatory and load-bearing ([`non-functional.md`](./non-functional.md) NFR-OPS-07); one verification command with a single meaning of "green" (NFR-OPS-08); the suite is written CI-ready so adding a pipeline is a configuration file, not a refactor (NFR-OPS-09). | **Whether to adopt CI before a second committer joins the repository.** Owner: product owner. The trigger is explicit: revisit before a second person commits. Azure DevOps is the preferred target if hosting lands on Azure with Entra ID. |
| ~~**RISK-003**~~ **CLOSED 2026-09-08 — resolved negative** | Neo4j **Enterprise** is a hard dependency: multi-database — the mechanism behind database-per-tenant — is not available in Community edition. | — | **No licence is available.** [ADR-0009](../adr/0009-logical-graph-partitioning.md) supersedes ADR-0002 for the graph store: single Community database, dual-encoded logical partitioning (tenant label + `tenant_id` property) behind a mandatory query builder. Community additionally has no RBAC (no database-level fallback) and no clustering (single instance, no HA). | — | Resolved as ADR-0002's own consequences section prescribed — superseded by a new ADR rather than worked around in code. Absorbed by Neo4j being a *derived* store (ADR-0003 rule 1): graph unavailable degrades retrieval to vector-only, graph lost rebuilds by re-index, and backup drops out of the critical path. | **None — closed.** Replaced by the standing **RISK-024**. |
| **RISK-024** | **Graph tenant isolation is enforced in application code, with no infrastructure or database-level fallback.** Three of four stores are defended by infrastructure; the graph is defended by a query builder, a static check and a post-retrieval re-filter. | **High** | This is the weakest isolation guarantee in the system and it protects the store whose output is quoted back to citizens. A query path added later without a matching negative test is an untested leak. Neo4j Community offers no RBAC, so unlike SQL Server — where ADR-0005's grant makes a mistake fail at the database — there is no second line. | Low per-release with the controls in place; rises with every new graph query path. | Dual encoding (label **and** property, asserted to agree); a mandatory tenant-aware query builder so unscoped Cypher is unwritable; a static build check banning Cypher literals outside `adapters/outbound/graph/` ([`tenant-isolation.md`](./tenant-isolation.md) NFR-SEC-25); retrieval re-filtered after leaving the graph so a leak must defeat three independent controls; a reconciliation job asserting label/property agreement and the absence of cross-tenant edges, since drift there is the early warning that precedes a leak; and a **negative test per graph query path** rather than one per store. | **None — this is a standing risk, not an open decision.** Reviewed at every release, owner Platform lead. Revisit ADR-0009 option D (move the graph into SQL Server, restoring physical isolation) if production traversals prove to be one or two hops — measure hop depth in UAT before treating Neo4j as settled. |
| **RISK-004** | UAE PASS onboarding is a long-lead procurement dependency; credentials cannot be self-provisioned. | **Medium** | Until it lands, citizen verification runs on the mock adapter. B11's step-up rules are configurable and tested but not exercised against real identity, so a green step-up suite is not proof that real verification works. Payments in production cannot be permitted on mocked verification ([`verification.md`](./verification.md) FR-VERI-09 prevents it at boot), so the payment journey cannot go live. | High that it is not ready when the code is, unless started now. | `VerificationProvider` port with a mock that implements every assurance level as a first-class fixture; the same suite validates the real adapter unchanged ([`verification.md`](./verification.md) FR-VERI-08). Boot-time refusal of the mock in production (FR-VERI-09) prevents the worst failure mode. | **Start UAE PASS onboarding now rather than when the code is ready.** Owner: product owner with the entity's integration authority. Also required: confirmation that OTP-only verification is an acceptable interim assurance level for any go-live that excludes payments. |
| **RISK-005** | The wireframe's grounding threshold drives two different behaviours at the same value: B12 refuses the answer and offers a human, while B7's handover node escalates automatically. The wireframe does not say which applies when both are configured. | **Medium** | Divergent implementations produce either a citizen who is refused and offered a handover that never arrives, or an automatic escalation outside staffed hours creating tickets nobody will pick up. Either is a visible service failure. | High without an explicit rule — the ambiguity is in the source. | **[ASSUMPTION] adopted:** below the threshold, if the active flow has a handover node and human agents are staffed and available, escalate automatically; otherwise refuse and present the configured no-agent-available message. Encoded in [`governance.md`](./governance.md) FR-GOV-05, [`flows.md`](./flows.md) FR-FLOW-06 and [`handover.md`](./handover.md) FR-HAND-16. | **DECIDED 2026-09-08 — confirmed as assumed.** Below the threshold, escalate automatically where the active flow has a handover node and agents are staffed and available; otherwise refuse and present the no-agent-available message. Avoids both failure modes — promising a handover nobody can take, and queueing tickets against an empty desk. FR-GOV-05, FR-FLOW-06 and FR-HAND-16 stand as written. |
| **RISK-006** | Assurance levels are inconsistently specified: B11 tab 2 lists four gated actions across three distinct levels, while ADR-0006 refers to "four assurance levels" and enumerates three. Emirates ID scan exists as a provider with no action requiring it. | **Low-medium** | An under-specified assurance ladder invites a per-feature interpretation, which is exactly how a payment gate gets weakened. The document-verified level currently gates nothing. | Certain — the contradiction is in the sources. | **[ASSUMPTION] adopted:** four levels L0–L3, with L3 (document-verified) defined for kiosk journeys and required by no seeded action. Encoded in [`verification.md`](./verification.md) FR-VERI-06. The mock implements all four so the ladder is testable before any real provider exists. | **Confirmation of the four-level ladder and whether any action should require L3** — most plausibly in-person kiosk account linkage. Owner: product owner. |
| **RISK-007** | "Arabic readiness" is two different numbers: 82% translation completeness (B10 tab 5) and 71% test accuracy (B13 tab 2). Both can block the same publish, for different reasons, but B13's summary strip cites only the accuracy failure. | **Low-medium** | A user who raises Arabic translation to 100% will still be blocked by the accuracy gate, and vice versa, with only one reason surfaced. That produces the exact experience the publish gate exists to prevent — a block that does not explain itself. | High without explicit handling. | [`evaluation.md`](./evaluation.md) FR-EVAL-08 and FR-EVAL-09 require each gate to name its own failing set, score and threshold; the block message must enumerate **every** failing condition, not the first. The two figures are held once each and read by the gate (FR-EVAL-15, [`non-functional.md`](./non-functional.md) NFR-I18N-03). | **None — resolved by requirement.** Recorded because a naive implementation reproduces the wireframe's single-reason message and would pass a shallow review. |
| **RISK-008** | Containment and deflection rates are reported but never defined, and the seeded figures place deflection consistently below containment, which inverts some common industry definitions. | **Low** | Two teams computing the same KPI differently makes the command centre's headline numbers unauditable, and any target set against them meaningless. | Certain — the definitions are absent from the source. | **[ASSUMPTION] adopted:** containment is the share of conversations resolved without human involvement; deflection is the share that would otherwise have become a channel contact. Deflection is a subset of containment, which matches the seeded figures. Published alongside every figure ([`analytics.md`](./analytics.md) FR-ANLY-12). | **Confirmation of both definitions and of the baseline each target is measured against.** Owner: product owner with the entity's analytics function. |
| **RISK-009** | B2 shows General FAQ Agent at v3.0 `Published` while B14 tab 1 shows Production running v2.4. "Published" (a registry lifecycle state) and "deployed to Production" (an environment state) are distinct, and the wireframe uses them adjacently without distinguishing them. | **Medium** | If conflated, a publish would implicitly deploy to Production, bypassing the promotion approval in B14 tab 1 — the change-control mechanism the governance screen exists to provide. | Medium — the conflation is an easy implementation error. | [`agents.md`](./agents.md) FR-AGENT-07 requires rollback and promotion to be distinct operations; FR-AGENT-18 publishes to a *selected environment*; [`governance.md`](./governance.md) FR-GOV-13 requires a promotion to name a specific version. A test asserts that publishing in UAT does not change what Production runs. | **None — resolved by requirement.** Recorded because the wireframe's own seeded data is the evidence that the two states must be separate, and because the version numbering scheme (what makes v1.3 become v1.4, and how a clone's v0.1 relates to it) remains unspecified and is assumed to be a monotonic minor increment per publish. |
| **RISK-010** | Four stores multiplied by tenant count, with no pipeline automating provisioning, makes tenant onboarding a four-store runbook rather than an operation. | **Medium** | A partially provisioned tenant is the one state in which the isolation reasoning breaks down (ADR-0002 rule 6). Manual onboarding under time pressure is how that state occurs. Qdrant collection count and SQL connection pools also grow linearly with tenants. | Medium, rising with tenant count. | Atomic provisioning with rollback ([`platform.md`](./platform.md) FR-PLAT-02); per-tenant bounded pooling ([`non-functional.md`](./non-functional.md) NFR-PERF-10); a resumable N-tenant migration orchestrator (FR-PLAT-05); a runbook in `../deployment.md`. | **Whether tenant provisioning should be exposed as an in-product operation for `Super Admin` rather than a runbook step.** Owner: product owner. Recommended, since FR-PLAT-02's atomicity is easier to guarantee in code than in a runbook. |
| **RISK-022** | **Retention is configured twice over the same rows.** `PrivacyConfigs.transcriptRetention` (B14 tab 4: 30d / 90d / 1y / **7y**) and `IdentityStitchingConfigs.memoryRetentionDays` (B11 tab 5: 30d / 90d / **1y**) both claim authority over derived conversation memory, with different option sets, in different modules, under different roles. | **Medium** | Taking the stricter of the two — the only safe reading, and what [`verification.md`](./verification.md) FR-VERI-13 implements as a single computed `retentionExpiresAt` — makes B14's 7-year transcript option **unreachable** whenever B11 is set, because B11's ceiling is 1 year. An administrator can therefore select a 7-year retention in the governance screen and silently get one year. A setting that cannot take effect is worse than a missing setting. | Certain — both controls exist in the wireframe with overlapping scope. | **[ASSUMPTION] adopted:** stricter-of-two, computed once (`../data-model.md` §10.5), so no row is retained longer than either setting permits. Recommended resolution: **retire `memoryRetentionDays`** and let B14 tab 4 be the single retention authority, with B11 tab 5 keeping only the *scope* control (per verified identity / per channel session / no memory), which is a genuinely different concern. | **DECIDED 2026-09-08 — recommendation accepted.** `IdentityStitchingConfigs.memoryRetentionDays` is **retired**. `PrivacyConfigs.transcriptRetention` (B14 tab 4) becomes the single retention authority over transcripts and derived memory; B11 tab 5 keeps only its *scope* control (per verified identity / per channel session / no memory), which is a genuinely different concern. FR-VERI-13's stricter-of-two resolution simplifies to a single source, and B14's 7-year option becomes reachable. |
| **RISK-023** | **The tool catalogue's tenancy scope is contradictory.** B5 describes the skills / MCP / connector catalogue as *"shared, platform-wide"*, yet B3 step 4B registers `mcp://customs.shj.ae` with mTLS credentials that plainly belong to Sharjah Customs, and B6 tab 1 establishes that sources are entity-owned and must not ground another entity's answers. | **Medium-high** | If read literally as platform-global, one government entity's MCP credentials and API connector secrets sit inside another entity's reach — a cross-entity credential exposure dressed up as a shared catalogue. If read as per-tenant, the genuinely cross-entity gateway (`mcp://sharjah-services.internal`, owner Platform) needs an explicit sharing mechanism that does not currently exist. | Certain — the contradiction is in the source. | **[ASSUMPTION] adopted:** modelled **per-tenant** (`../data-model.md` §14), reading "platform-wide" as "estate-wide within the entity". The Platform-owned gateway is registered in the platform tenant; making it callable by other tenants would require an explicit share, which would need its own ADR. Per-tenant is the correct default because the failure mode of the alternative is credential exposure. | **DECIDED 2026-09-08 — confirmed as modelled.** Tool registrations are **entity-owned**: `Skills`, `McpServers` and `ApiConnectors` are per-tenant, and B5's "platform-wide" reads as *estate-wide within the entity*. The Platform-owned gateway is registered in the platform tenant. **No cross-entity share mechanism** is built; adding one later requires its own ADR. Chosen because the failure mode of the alternative is one entity's mTLS credentials being reachable by another. |
| ~~**RISK-025**~~ **CLOSED 2026-09-08 — resolved** | `prisma/sql/001_constraints.sql`'s idempotency guards (`IF NOT EXISTS (SELECT 1 FROM sys.check_constraints WHERE name = …)`) check by constraint name only, with no schema qualification. A constraint name is unique **per schema**, not per database, so once the first-provisioned tenant has a given check constraint, every later tenant's identically-named guard reports "already exists" and silently skips creating it for that tenant. | — | **Fixed.** Audited every `IF (NOT) EXISTS` idempotency guard in the file's tenant section (after `SECTION BOUNDARY`): 311 of 362 `sys.check_constraints` guards were unscoped and vulnerable (the other 51, in the platform section, target one fixed schema and were never at risk); all 70 `sys.indexes` guards were already correctly scoped via `object_id = OBJECT_ID(...)`; `sys.database_principals` (login existence) and `sys.fulltext_catalogs` checks are database-wide objects, not schema-scoped, so unaffected; every `CREATE OR ALTER TRIGGER`/`PROCEDURE` embeds `[{{SCHEMA}}]` in the object name itself and was never vulnerable. All 311 rewritten to add `AND parent_object_id = OBJECT_ID('[{{SCHEMA}}].[Table]')`, matching the pattern ADR-0011's 5 new FK checks already used. | — | Two probe tenant schemas provisioned directly via `SqlStoreProvisioner` (independent of the ADR-0011 fix's own verification): both ended up with identical constraint sets — 311/311 `sys.check_constraints` and 163/163 `sys.foreign_keys`, zero missing in either direction, confirmed for the specific previously-broken constraints named in this row. `pnpm exec vitest run --project isolation` (26/26) and `node scripts/verify.mjs --staged` (14/14) both re-run clean against the live stack after the fix. | **None — closed.** |
| **RISK-026** | **The Pipeline Designer ([`orchestration.md`](./orchestration.md) §5.5.2) has no automated end-to-end coverage.** Its pure domain logic is unit-tested on both sides (`apps/ai/tests/domain/test_pipeline.py`, `test_condition_expr.py`, `apps/ai/tests/application/test_execute_pipeline.py`, and `apps/web`'s per-file `.test.ts`/`.test.tsx` suite covering every port, use-case and canvas component), but no `e2e/**/*.spec.ts` exercises the drag-and-drop canvas, the publish flow, or the activation flow through a real browser against the real running Docker stack, despite reusable e2e infrastructure already existing (`e2e/journeys/*`, `e2e/backoffice/*`, session-minting via `scripts/mint-e2e-sessions.ts`). | **Medium-high** | Four real, user-facing defects shipped and were only caught because a human tested manually in a browser and reported the exact error text: a stale generated Prisma client after a schema change (missing a container-only Docker volume regenerate), a corrupted `.next` build cache causing a global 500 on every route including the health check, pipeline nodes all landing at canvas position `(0,0)` causing `@xyflow/react`'s `fitView` to collapse to a zero-area box (rendering as an empty canvas), and a `flex-1`-inside-a-column-flex-container CSS defect that also collapsed the canvas to zero height regardless of node data. None of the four would have been caught by the existing unit-test suite, because none of them is a pure-domain-logic defect — all four are integration, infrastructure or rendering defects, exactly the class of bug E2E testing exists to catch. Per this document set's own Phase D rule ("a requirement with no passing test is an incomplete requirement"), [`orchestration.md`](./orchestration.md) FR-ORCH-15 through FR-ORCH-30 are implemented and were manually/live-verified during this delivery, but are not yet provably regression-proof. | High that a future change to the canvas, the publish flow or the activation flow regresses silently, since nothing but manual testing would catch it. | The four found defects are fixed and the underlying domain logic is unit-tested; what remains is authoring `e2e/backoffice/pipeline-designer.spec.ts` (or similar) reusing the existing session-minting and fixture infrastructure to drive: create a pipeline → drag two agents onto the canvas → wire them → attempt to publish an invalid graph and see the findings panel → fix it and publish → activate it → confirm the legacy execution-mode panel disables. | **Author the missing Pipeline Designer E2E spec before this feature is considered release-complete.** Owner: whoever picks up the next wave of this delivery. This is the single largest gap between "built and manually verified" and "done" per this project's own Phase D standard. |
