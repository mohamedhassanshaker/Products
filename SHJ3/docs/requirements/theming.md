# 5.16 `theming` — in-product theming and skinning (Phase E, ADR-0007)

Mandatory in-product module, beyond the wireframe. Theming is a runtime capability, not a build-time configuration file.

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-THEME-01 | The system shall provide a theming module reachable from *Settings → Appearance*, and a tenant branding surface for principals authorised to change tenant-level theming. | Phase E | MUST | The route exists and is permission-gated. A user without tenant-branding rights sees and edits only their own preference; an authorised admin sees the tenant surface. |
| FR-THEME-02 | The system shall express every themable value as a runtime CSS custom property across three layers — primitive, semantic, component — and feature code shall reference only semantic and component tokens. | ADR-0007 token contract | MUST | Feature code contains no literal colour, radius, spacing, shadow or font-size value and no direct primitive reference. Verified mechanically, not by review. |
| FR-THEME-03 | The system shall apply a token change across the entire application at runtime, without a rebuild, redeploy or per-component override. | Phase E; ADR-0007 | MUST | Changing a semantic token repaints every screen in the running application. No component carries a private copy of a themable value. |
| FR-THEME-04 | The system shall allow an authorised user to set brand values: primary, secondary and accent colours; the semantic colours success, warning, danger and info; a light-variant and a dark-variant logo; a favicon; and the application title. | Phase E | MUST | All eleven values persist and are applied. The application title and logo are read from tokens, satisfying brief requirement R2 as configuration rather than as hardcoded branding. |
| FR-THEME-05 | The system shall allow an authorised user to set typography: font family, base size, type scale and weight. | Phase E | MUST | Each value persists and changes rendered text across the application. A font family without a valid fallback stack is rejected. |
| FR-THEME-06 | The system shall allow an authorised user to set layout values: corner radius, spacing density from `compact` or `comfortable`, shadow depth and sidebar style. | Phase E | MUST | Switching density changes spacing globally through tokens, not through per-screen overrides. All four values persist per scope. |
| FR-THEME-07 | The system shall support display modes `light`, `dark` and `system`, where `system` follows the viewer's operating-system preference. | Phase E | MUST | All three modes render correctly. Under `system`, changing the OS preference changes the application without a reload. Every token has a defined value in both modes. |
| FR-THEME-08 | The system shall support text direction `LTR` and `RTL`, tied to language selection, applied through logical CSS properties. | Phase E; ADR-0007 | MUST | Selecting Arabic sets `dir="rtl"` and mirrors layout, including the assistant thread, the sidebar and the wizard step strip. No physical direction property appears in the codebase. This closes the wireframe's §8 RTL gap. |
| FR-THEME-09 | The system shall support named skins as saveable presets, shipping at least a default and a dark skin, and shall allow an authorised user to duplicate and edit a skin. | Phase E | MUST | Both shipped skins exist and are selectable. Duplicating produces an independent copy; editing the copy does not alter the original or the shipped skins, which are not editable in place. |
| FR-THEME-10 | The system shall export a skin as a JSON document conforming to a versioned schema. | Phase E; ADR-0007 | MUST | Exporting produces a document carrying a schema version, the semantic token values and asset references. Round-tripping an export through import reproduces the skin exactly. |
| FR-THEME-11 | The system shall validate an imported skin against the schema and against the contrast rules before applying it, treating an imported skin as untrusted input. | ADR-0007 | MUST | A malformed skin is rejected naming the offending field. A schema-valid skin failing contrast is rejected naming the failing token pair and its ratio. No partial import is ever applied. |
| FR-THEME-12 | The system shall render theming changes as a live preview with explicit save and reset actions, and shall never leave the application in a partially applied state. | Phase E | MUST | Editing shows changes immediately; navigating away without saving discards them; reset restores the last saved state. An interrupted save leaves the previous theme intact. |
| FR-THEME-13 | The system shall resolve the effective theme in the order *user preference → tenant theme → system default*. | Phase E; ADR-0007 | MUST | With all three present the user preference wins; removing it falls back to the tenant theme; removing that falls back to the system default. The resolved origin is inspectable. |
| FR-THEME-14 | The system shall resolve the theme server-side on first paint and inline the resolved token set into the document head, so no tenant branding is fetched client-side. | ADR-0007 | MUST | The first paint carries the correct theme with no flash of the default. No network request for tenant theme data is observable from the client. |
| FR-THEME-15 | The system shall store tenant theme data within the tenant's own schema and shall never render one tenant's branding to a principal of another tenant. | ADR-0007; ADR-0002 | MUST | A cross-tenant branding leak test loads pages as principals of two tenants in sequence, including through a shared cache, and observes no bleed. Covered by the isolation gate in [`tenant-isolation.md`](./tenant-isolation.md). |
| FR-THEME-16 | The system shall compute WCAG 2.1 AA contrast for every foreground/background token pair at save time, blocking the save for text pairs below the threshold and warning for non-text pairs. | Phase E; ADR-0007 | MUST | A theme with 3:1 body-text contrast is refused, naming the pair and the measured ratio. A non-text pair below threshold warns and may be saved. The check runs on save and on import (FR-THEME-11). |
| FR-THEME-17 | The system shall provide a one-click restore to the default theme at every scope, available even when the current theme renders the interface unreadable. | Phase E | MUST | Restore is reachable by keyboard from any screen and does not depend on reading low-contrast text. After restore, the default skin is active at that scope. |
| FR-THEME-18 | The system shall define theming authority explicitly: an end user may set their own preference; a tenant administrator may set the tenant theme; only a `Super Admin` may change the system default. | Phase E | MUST | Each scope is writable only by its authorised role, enforced server-side. **[ASSUMPTION]** — Phase E requires the question to be answered; the answer is per-user preference plus per-tenant branding, with white-labelling per tenant supported. |
| FR-THEME-19 | The system shall enforce token compliance mechanically, failing the build on an arbitrary style value or a physical direction property in feature code. | ADR-0007 | MUST | Introducing a literal colour, an arbitrary spacing value or a physical direction property fails the lint gate. The rules are present in the first commit, not retrofitted. |
| FR-THEME-20 | The system shall resolve the web widget's accent colour and other channel-level appearance settings through the same token system as the backoffice. | B10 tab 2; ADR-0007 | MUST | Changing the widget accent in B10 tab 2 sets a token value; the widget carries no independent colour implementation. The widget respects tenant branding and the citizen's mode preference. |
