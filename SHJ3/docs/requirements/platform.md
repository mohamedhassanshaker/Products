# 5.1 `platform` — tenancy substrate, provisioning, configuration

Substrate module. No wireframe screen; derived from ADR-0002, ADR-0005 and ADR-0008. Everything may depend on it; it depends on nothing.

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-PLAT-01 | The system shall maintain a tenant registry in which each tenant is one Sharjah government entity, holding at minimum a stable id, a validated slug, a display name, an entity-scope flag, and provisioning status per store. | ADR-0002; B9 tab 2 | MUST | Registry seeded with `sewa`, `customs`, `libraries`, `platform`. Slug matches `^[a-z][a-z0-9_]{2,31}$`. A slug failing validation is rejected before any connection string is built. |
| FR-PLAT-02 | The system shall provision a tenant atomically across all four stores — SQL Server schema, Neo4j database, Qdrant collection, Redis key prefix — or roll all four back, leaving no half-provisioned tenant. | ADR-0002 rule 6 | MUST | Inject a failure at each of the four steps in turn; after each run the tenant is absent from all four stores and the registry records `failed`, never `active`. |
| FR-PLAT-03 | The system shall derive every store handle name from the registered tenant slug and shall never interpolate a name from request input. | ADR-0002 rule 4 | MUST | No connection string, database name, collection name or key prefix is built from a header, query param, route param or body field. A negative test with an injection payload in a tenant field returns 403 without touching any store. |
| FR-PLAT-04 | The system shall de-provision a tenant by dropping its SQL schema, Neo4j database, Qdrant collection and Redis key prefix, reporting completion per store. | ADR-0002 consequences; B14 tab 4 | MUST | After de-provision all four stores report the unit absent. The operation is idempotent and audited. |
| FR-PLAT-05 | The system shall apply schema migrations per tenant through a resumable orchestrator that records per-tenant status and can restart after a partial failure without re-applying completed tenants. | ADR-0005 rule 2 | MUST | Kill the orchestrator mid-run across three tenants; on restart only unapplied tenants are touched and the final state is identical to an uninterrupted run. |
| FR-PLAT-06 | The system shall resolve configuration in the order *tenant-specific value → platform default*, and shall record which level supplied each resolved value. | ADR-0002; B12 tabs 1–2 | MUST | A tenant override wins over the platform default; with no override the platform default applies; the origin level of each resolved value is inspectable. |
| FR-PLAT-07 | The system shall treat the `Platform` tenant as scoped to all entities for read purposes, and shall serve cross-tenant reads only through the two designated escape hatches. | B9 tab 2; ADR-0002 rule 5 | MUST | A `Platform`-scoped Super Admin can produce a cross-tenant analytics rollup; the same principal cannot read another tenant's agents, sources or transcripts through any feature-module endpoint. |
| FR-PLAT-08 | The system shall expose exactly two cross-tenant escape hatches — tenant provisioning and cross-tenant analytics rollups — both restricted to `Super Admin` and both writing an audit entry on every invocation. | ADR-0002 rule 5 | MUST | Both endpoints deny non-Super-Admin principals. Each invocation produces exactly one audit entry naming actor, hatch and scope. A test enumerating the route table finds no third cross-tenant path. |
| FR-PLAT-09 | The system shall validate required configuration and secrets at boot and shall refuse to start when any required value is absent or malformed. | architecture §10 | MUST | Removing any required environment variable causes a non-zero exit with a message naming the missing key. The process never starts partially configured. |
| FR-PLAT-10 | The system shall provide a deterministic seed data set covering the wireframe fixtures — four tenants, four agents, four knowledge sources, five users, two seeded source conflicts, the open SEWA breaker, the four routing rules and the four golden sets — reproducible identically across runs. | ADR-0008; guide §1.3 | MUST | `docker compose up` twice from empty volumes produces identical seed state. At least two tenants are provisioned so isolation is exercisable locally. E2E tests assert against these fixtures. |
