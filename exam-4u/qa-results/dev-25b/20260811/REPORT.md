A real Chromium browser (Playwright) was launched with `--host-resolver-rules=MAP *.examland.local 127.0.0.1` so the tenant's subdomain (`qadev25b<suffix>.examland.local`) resolved to the local dev server without needing a hosts-file edit (note: `*.examland.app`, the project's actual convention, could not be used for this browser leg specifically because `.app` is on Chromium's built-in HSTS-preload list and forces HTTPS even for a plain `http://` dev URL — an artifact of this QA pass's own tooling choice, not a product defect; confirmed via code read that `TenantResolutionMiddleware` only ever inspects the first DNS label of the `Host` header, so the apex domain choice has no bearing on the tenant-resolution logic itself).

Screenshots retained at `qa-results/dev-25b/20260811/screenshots/` (this report's own directory, not the Windows temp used for earlier phases). All ad hoc tenant/platform MySQL schemas and ad hoc server processes were dropped/killed after the run; confirmed via `SHOW DATABASES` and `netstat` afterward that nothing was left behind.
- Also ran, unmodified: `apps/api` full unit suite, `apps/web` full unit suite, `apps/api/test/pdf-image-rendering.e2e-spec.ts` (real MySQL/HTTP), `npm run lint`, `npm run typecheck` (both workspaces).

## What was independently verified

1. **Real-browser image rendering, end to end (the orchestrator's primary ask).** Logged in as a real Admin in a real Chromium browser, navigated to the real PDF review screen (`/pdf-processing/sessions/:id`), and confirmed a genuine `<img>` renders inline beneath the question text — not a broken-image icon, not a placeholder box. Inspected the actual `src` attribute directly via the DOM: `/api/files/d/tenants/<tenantId>/pdf/<sessionId>/images/<sha256>.png?exp=<epoch>&sig=<hmac>` — a real signed delivery path from Dev-17a's mechanism (tenant-scoped, content-hash-named, time-limited, HMAC-signed), never a raw/guessable path. Expanded the row's inline editor and confirmed the same image renders again at the larger 320px cap in its own labeled "Images" sub-section, per UX §14.1. Then logged in as a real Member, started a real attempt against the finalized Exam Type, and confirmed the identical image renders on the exam-taking screen (`/attempts/:id/take`) between the question heading and the radio-group options, again via a genuine signed `<img src>` (a different, freshly re-signed URL each time — confirming `InlineImageComponent`'s own `sign()`-per-mount behavior, not a cached/reused URL). Screenshots: `03-review-screen-collapsed.png`, `04-review-screen-expanded.png`, `07-attempt-take-with-image.png` (all show the actual crimson test-PNG rendered inline, not a broken-image glyph). No browser console errors or failed requests were observed during any of these navigations.
2. **Alt text WCAG check, in the real browser.** Read the live DOM `alt` attribute directly (not just a unit-test assertion) on both the review-screen and exam-taking-screen `<img>` elements: `"Image from page 1 of the source document."` on both — real, non-empty, human-readable text, never a bare `alt="image"` or an empty string. Matches UX §14.4's documented, deliberate placeholder wording exactly and Dev-25b's own claim.
3. **MySQL 8.x `ORDER BY ... NULLS LAST` fix.** Read `question-image.repository.ts` directly: both `findForQuestion` and the new `findForQuestions` now order via `.orderBy('(qi.sequence_order IS NULL)', 'ASC')` (an `IS NULL`-emulation, portable SQL) instead of TypeORM's `'NULLS LAST'` literal third argument, which MySQL 8.x rejects. Independently re-ran the full apps/api unit suite (includes the regression-guard test asserting the literal string `'NULLS LAST'` never reappears) and re-ran `test/pdf-image-rendering.e2e-spec.ts` against real MySQL 8.x — both green, confirming the fix works against a real server, not just an in-memory mock. This phase's own e2e pipeline (real PDF upload → real association write → real `GET .../questions` read) is itself proof the previously-latent `ER_PARSE_ERROR` no longer fires.
4. **Removal-race non-exposure.** Grepped every non-spec source file calling into `ImageAssociationService`: `PdfProcessingService`/`ImageExtractionService` call only `associateWithQuestion`; `QuestionReviewService` and `AttemptsService` call only the new read-only `listImagesForQuestions`. No controller, service, or route anywhere in `apps/api/src` calls `associateWithQuestion`'s sibling `removeAssociation`/`removeAssociationAndCleanupStorage` outside of the services' own spec files and the deliberate e2e coverage. Confirmed no new HTTP route exists for media removal (`grep`'d all `@Delete`/`@Post` decorators reachable from `files`/`pdf-processing`/`attempts` controllers — none touch image association). Dev-25a's QA-flagged concurrent-duplicate-removal race (`QuestionImageRepository.deleteAndReturn`'s non-atomic find-then-delete) genuinely remains unreachable in production after this phase, exactly as both nexus-dev's and Dev-25a QA's own notes state.
5. **Signed-URL enforcement.** Confirmed via the real browser DOM (not just code read) that every rendered `<img src>` is always an `/api/files/d/...?exp=...&sig=...` signed path. Read `InlineImageComponent.ts`: the *only* way it ever sets `url` is via `FilesService.sign(storageKey)`'s response — there is no code path that constructs a `/files/d/...` URL directly from `storageKey` client-side. Read `AvatarComponent.ts` for comparison: confirmed `InlineImageComponent` and `AvatarComponent` remain the only two files in `apps/web/src` importing `FilesService.sign` (`grep -rl "filesService.sign\|FilesService" apps/web/src` shows no third caller). Server-side, `pdf-image-rendering.e2e-spec.ts` (re-run, green) explicitly asserts the `storageKey` returned by `GET .../questions` is never itself a working download path — it only becomes one after the `POST /files/sign` round trip.
6. **Full unit suite re-run.** `apps/api`: **171 suites / 1447 tests, all green** (exactly matches nexus-dev's reported numbers), ~208s. `apps/web`: **57 suites / 308 tests, all green** (exactly matches nexus-dev's reported numbers), ~50s. `npm run typecheck` clean on both workspaces; `npm run lint` (project-wide, `--max-warnings=0`) clean. Did not additionally re-isolate the 3 pre-existing-flaky suites nexus-dev names (`pdf-processing.service.spec.ts`'s AI-outage timeout flake, `pdf-image-extractor.spec.ts`'s `--experimental-vm-modules` sandbox limitation) beyond observing they passed cleanly in this pass's own full-suite run (both root-caused and reconfirmed unrelated by two prior QA passes — Dev-23's and Dev-24's — with no code in this phase touching either file); not re-litigated further given no new evidence to distrust the prior findings this time.
7. **`pdf-image-rendering.e2e-spec.ts` re-run.** Re-ran unmodified against real MySQL: **2/2 tests green.** Confirmed by direct inspection of the test output that it does what it claims — the review-screen test asserts `image.altText` is non-empty and not the bare word "image", asserts `image.position === 'question_text'`, and performs a genuine `POST /files/sign` → `GET /files/d/...` round trip returning `content-type: image/*` and non-zero bytes; the exam-taking test additionally proves the same image is reachable from a live attempt via the new `attempt_question.source_generated_question_id` link and survives to the post-submit review. Both properties were independently re-confirmed in the real-browser pass above, not just trusted from the e2e assertions alone.

## Defects found

None blocking. No new defects were found in this phase's own scope; Dev-25a's previously-flagged non-blocking concurrency defect (`QuestionImageRepository.deleteAndReturn`'s non-atomic find-then-delete) was independently re-confirmed to remain unreachable after this phase (see item 4 above) — still flagged for whoever eventually builds the deferred manual add/remove media endpoint, not a blocker for Dev-25b or for closing out BL-24.

Two pre-existing, explicitly-disclosed, non-blocking product/content gaps carried forward from nexus-ux's own UX_GUIDELINES.md §14.8 flags (not defects — deliberately out of this phase's scope, already flagged to product by nexus-ux and nexus-dev):
- Flag 65: placeholder alt text ("Image from page N...") is honest but not fully WCAG 1.1.1-equivalent for a sighted user's experience — product needs to decide between an AI-vision-captioning follow-up or accepting this as a permanent tradeoff.
- Flags 66/67: no lightbox/full-size expansion in the review screen, no tap-to-zoom on the exam-taking screen's mobile-reduced image — both explicitly out of scope for this phase, not asked for.

**Ready — Dev-25b is QA-green, no blocking defects.
