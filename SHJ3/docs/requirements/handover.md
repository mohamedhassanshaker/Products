# 5.9 `handover` — escalation queue, routing rules, live agent workspace (B8)

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-HAND-01 | The system shall record live agent presence as `Available`, `Busy` or `Offline`, settable by the agent, and shall offer tickets only to `Available` agents. | B8 agent status | MUST | Setting `Offline` removes the agent from routing targets immediately. Presence is per tenant and is not inferred from session activity alone. |
| FR-HAND-02 | The system shall maintain an escalation queue showing per ticket the user, topic, channel, waiting time and priority. | B8 queue | MUST | The three seeded tickets render with all five fields. Waiting time increments live. Priority is one of `Normal`, `High`. |
| FR-HAND-03 | The system shall load a ticket's full transcript and context rail on selection. | B8 | MUST | Selecting each seeded ticket loads that ticket's transcript and its own context, with no data from another ticket. |
| FR-HAND-04 | The context rail shall show the customer's account or case reference and their verification state. | B8 per-ticket detail | MUST | The three seeded tickets show, respectively, a verified SEWA account, an unverified declaration reference, and no membership on file. Verification state comes from the `verification` module, not from free text. |
| FR-HAND-05 | The system shall display the escalation reason prominently on every ticket, drawn from the three distinct triggers: tool failure, explicit user request, and low grounding confidence. | B8 `[rule]` | MUST | Each of the three reasons is produced by its own trigger path and is rendered as structured data, not prose. A ticket with no recorded reason cannot be created. |
| FR-HAND-06 | The system shall insert a system note into the transcript marking the point at which control transferred to a human. | B8 | MUST | The note appears exactly once, at the handoff position, and is distinguishable from user and assistant turns in both the workspace and the citizen thread. |
| FR-HAND-07 | The system shall offer canned replies scoped to the ticket's topic, and selecting one shall populate the composer without sending. | B8 | MUST | Billing tickets offer billing replies only. Selecting a reply fills the composer, leaves it editable, and sends nothing until the agent submits. |
| FR-HAND-08 | The system shall evaluate routing rules as an ordered list from top to bottom, where the first enabled matching rule wins and no later rule is evaluated. | B8 routing rules | MUST | The four seeded rules evaluate in order. A ticket matching rules 1 and 2 routes by rule 1. Evaluation short-circuits — asserted by instrumentation, not inferred from the result. |
| FR-HAND-09 | The system shall reorder routing rules, and the new order shall govern subsequent evaluation. | B8 | MUST | Moving rule 2 above rule 1 causes a Billing + High ticket to route to senior agents instead of the billing team. Order is persisted, not view-local. |
| FR-HAND-10 | The system shall enable and disable individual routing rules, and disabled rules shall be skipped during evaluation while retaining their position. | B8 | MUST | Disabling rule 1 causes a Billing ticket to fall through to the next matching rule. Re-enabling restores the original outcome without re-entering the rule. |
| FR-HAND-11 | The system shall create and edit routing rules through a form capturing a condition attribute from `Topic`, `Priority`, `Channel`, `Wait time`, an operator that defaults to `>` for `Wait time` and `=` otherwise, a value, and a route target; the edit form shall open pre-filled. | B8 | MUST | Selecting `Wait time` switches the operator to `>`; selecting any other attribute switches it to `=`. Editing rule 3 opens with its current values. Invalid attribute/operator pairs are rejected server-side. |
| FR-HAND-12 | The system shall delete a routing rule, closing the ordering gap. | B8 | MUST | After deleting rule 2, the remaining rules are contiguously ordered and evaluation reflects the new sequence. |
| FR-HAND-13 | The system shall provide a rule tester that accepts a composed sample ticket — topic, priority, channel, wait time — and evaluates it against the live rule list including unsaved reordering, enabling and edits. | B8 rule tester | MUST | Reorder rules and run the tester without saving; the result reflects the pending order. The tester performs no routing and creates no ticket. |
| FR-HAND-14 | The rule tester shall report which rule fired and where the ticket routes, or state that no rule matched and the ticket falls to the default queue. | B8 rule tester | MUST | Both outcomes are produced by the tester and are distinguishable. The firing rule is named by number and condition, not merely by target. |
| FR-HAND-15 | The system shall route a Billing + High-priority ticket to the billing team while the topic rule precedes the priority rule, and to senior agents once the priority rule is moved above it. | B8 `[rule]` | MUST | Both outcomes are asserted in one test that performs the reorder between assertions. This is the canonical proof that order determines outcome. |
| FR-HAND-16 | The system shall offer escalation to a human only within configured human-agent working hours, and shall present the configured no-agent-available message outside them. | B10 tab 1 `[rule]` | MUST | Outside staffed hours, a handover trigger produces the configured message and does not create a queued ticket the citizen is told to wait for. Inside staffed hours the ticket is created. |
| FR-HAND-17 | The system shall transfer the full transcript, the identity and assurance state, and any pending slot when a conversation escalates. | A3 `[rule]`; B8 | MUST | A ticket escalated at the account-number step carries all prior turns, the citizen's assurance level, and `awaiting slot: account_number`. Nothing in the escalation path summarises or truncates the transcript. |
| FR-HAND-18 | The system shall require the `Handle escalations` permission to view or act on the queue. | B9 tab 3 | MUST | An Analyst receives 403 on every queue endpoint. A Live Agent succeeds. A Live Agent has no dashboard access, matching the seeded matrix. |
| FR-HAND-19 | The system shall support a routing rule that, on a wait-time threshold, re-queues the ticket and raises a supervisor alert, with a bounded number of re-queues before the ticket is escalated by priority instead of re-queued. | B8 rule 4 | MUST | A ticket waiting beyond the threshold is re-queued and an alert is raised. **[ASSUMPTION]** — the wireframe does not bound the loop; the bound is two re-queues, after which priority is raised to `High` and no further re-queue occurs. Without the bound the rule can loop indefinitely. |
| FR-HAND-20 | A handover node firing in a flow shall create exactly one escalation ticket carrying the trigger that fired as its escalation reason, so the flow definition and the operational queue always agree. | `flows` → `handover`; B7 → B8 | MUST | Fire the low-confidence trigger: one ticket appears with reason "low grounding confidence" and the measured confidence. Fire the tool-failure trigger: one ticket with reason "tool call failed twice". No ticket exists without a trigger, and no fired trigger exists without a ticket. *(Cross-module invariant; also listed in [`cross-module.md`](./cross-module.md).)* |
| FR-HAND-21 | The rule tester shall evaluate the same ordered, enabled rule set that production routing evaluates, including changes not yet saved, so a tester result and a live routing decision cannot differ for identical input. | `handover`; B8 within-screen | MUST | Reorder rules, run the tester, save, then route a real ticket with identical attributes: the outcomes match. A test drives the same input through both the tester and the routing path and asserts equality — the tester and the router share one evaluation implementation. *(Cross-module invariant; also listed in [`cross-module.md`](./cross-module.md).)* |
