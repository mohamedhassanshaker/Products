# 5.10 `channels` — channels, widget studio, WhatsApp, campaigns, locales (B10, A1)

Satisfies brief requirement R8.

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-CHAN-01 | The system shall maintain the channels `Web widget`, `WhatsApp`, `Mobile app` and `Kiosk / IVR`, each with a bound agent, operating hours and a state of `Live` or `Disabled`. | B10 tab 1 | MUST | All four channels are present with the seeded bindings and states. Mobile app and Kiosk/IVR ship `Disabled` with no bound agent. |
| FR-CHAN-02 | The system shall stop new conversations immediately on disabling a channel while allowing conversations already open on it to complete. | B10 tab 1 `[rule]` | MUST | Disable a channel with an open conversation: the open conversation accepts further turns to completion, and a new session on that channel is refused with the configured message. |
| FR-CHAN-03 | The system shall configure assistant availability hours and human-agent working hours independently. | B10 tab 1 `[rule]` | MUST | The assistant serves turns 24/7 while escalation is refused outside staffed hours ([`handover.md`](./handover.md) FR-HAND-16). Changing one set of hours does not change the other. |
| FR-CHAN-04 | The system shall configure human-agent working hours per weekday and shall auto-synchronise UAE public holidays as non-working days. | B10 tab 1 | MUST | The seeded schedule (Sun–Thu 08:00–20:00, Sat 09:00–14:00) is configurable. A synchronised public holiday suppresses escalation for that date without a manual edit. Holiday sync failure degrades to the weekday schedule and is logged. |
| FR-CHAN-05 | The system shall provide a toggle keeping the assistant available when no human agent is on shift, together with the message shown when no agent is available. | B10 tab 1 | MUST | With the toggle on and no agents available, the assistant answers and the configured message replaces the offer of a handover. With it off, out-of-hours sessions are refused with that message. |
| FR-CHAN-06 | The system shall configure the web widget's accent colour, launcher position, default state, disclaimer text, greeting text and composer placeholder. | B10 tab 2 | MUST | All six settings persist and are honoured by the rendered widget. Accent colour is written as a theme token, not as a literal in widget code (FR-THEME-20). |
| FR-CHAN-07 | The system shall render a live preview of the widget that reflects every configuration change without a save. | B10 tab 2 | MUST | Changing the accent colour updates the preview's header indicator, bubble tint and chip borders immediately. The preview uses the same components as the live widget, not a facsimile. |
| FR-CHAN-08 | The system shall generate an embed snippet carrying the current widget configuration, with a copy action that confirms success. | B10 tab 2 | MUST | The snippet reflects the current configuration, embeds correctly in a plain HTML page, and the copy action reports completion. The snippet contains no secret. |
| FR-CHAN-09 | The system shall maintain an allowlist of domains permitted to embed the widget and shall refuse to initialise on an origin outside it. | B10 tab 2 | MUST | Embedding on `sharjah.ae` initialises; embedding on an unlisted origin refuses and creates no session. The check is server-side on session creation, not only in the client script. |
| FR-CHAN-10 | The system shall configure the WhatsApp channel with its business number, its BSP, an opt-in requirement toggle and its session-window duration. | B10 tab 3 | MUST | All four settings persist. The BSP is configured behind an adapter so a change of provider does not alter channel logic. |
| FR-CHAN-11 | The system shall track the WhatsApp 24-hour session window, permitting free-form replies within it and requiring an approved template to re-open contact after it closes. | B10 tab 3; A1 | MUST | Within the window a free-form reply sends. After it closes a free-form send is refused and a template send succeeds. The window state is surfaced to staff and to the citizen thread. |
| FR-CHAN-12 | The system shall maintain a message template registry with statuses `Approved` and `Pending review`, and newly submitted templates shall enter as `Pending review`. | B10 tab 3 | MUST | The three seeded templates render with their statuses. Submitting a new template with a name and sample body creates it as `Pending review`; it cannot be used for an outbound send. |
| FR-CHAN-13 | The system shall maintain proactive messaging campaigns recording template, trigger, audience, sent volume and state. | B10 tab 4 | MUST | The three seeded campaigns render with all five fields. A campaign references a template by identity, not by name string. |
| FR-CHAN-14 | The system shall set a campaign to `Blocked` while its template is not `Approved`, and shall refuse to enable a blocked campaign. | B10 tab 4 `[rule]` | MUST | The appointment-confirmation campaign is `Blocked`. Attempting to enable it fails server-side, not only in the UI, and the failure names the unapproved template. |
| FR-CHAN-15 | The system shall unblock a campaign automatically when its template becomes `Approved`, without a further edit to the campaign. | B10 tab 4 `[rule]`; [`cross-module.md`](./cross-module.md) | MUST | Approving `appointment_confirmation` changes its campaign from `Blocked` to enableable on the next read. The dependency is enforced by the domain rule, not reproduced in two places. |
| FR-CHAN-16 | The system shall verify both an approved template and a recorded opt-in at send time for every outbound message, and shall refuse the send when either is absent. | B10 tab 4 `[rule]` | MUST | Revoke a recipient's opt-in after campaign configuration; their next scheduled send is refused and recorded as suppressed. Revoke a template's approval; all sends using it are refused. Checks occur at send time, not only at configuration time. |
| FR-CHAN-17 | The system shall suppress outbound sends during configured quiet hours and shall queue or drop them according to configuration rather than sending late silently. | B10 tab 4 | MUST | With quiet hours 21:00–07:00, a send falling in that window is not delivered inside it, and its disposition — queued to the window's end, or dropped — is recorded. |
| FR-CHAN-18 | The system shall maintain a locale registry recording per locale the voice, text direction, translation completeness percentage and fallback status. | B10 tab 5 | MUST | English (LTR, 100%) and Arabic (RTL, 82%) render with all four fields. Translation completeness is computed from the message catalogue, not stored by hand. |
| FR-CHAN-19 | The system shall designate exactly one fallback locale, used when a requested locale has no translation for a given string. | B10 tab 5 | MUST | Setting Arabic as fallback moves the designation off English. A string missing in the requested locale renders in the fallback locale and the miss is counted. |
| FR-CHAN-20 | The system shall adapt rendering structurally per channel, using each channel's native components rather than approximating the web components. | A1 `[rule]` | MUST | On WhatsApp, suggestion chips render as list-message rows; on web they render as chips. The same conversation on both channels produces channel-appropriate structures from one flow definition. |
| FR-CHAN-21 | The system shall present the opt-in notice and honour an opt-out keyword on WhatsApp, recording the opt-out against the recipient. | A1 WhatsApp state | MUST | The opt-in notice renders on the first message. Replying with the opt-out keyword records the opt-out and suppresses all subsequent outbound sends (FR-CHAN-16). |
| FR-CHAN-22 | The system shall surface the WhatsApp session-window state in the citizen thread, since it governs whether a free-form reply is permitted. | A1 `[rule]` | SHOULD | The thread shows that the window is open while it is. When it closes, the citizen-visible state changes rather than a send failing without explanation. |
| FR-CHAN-23 | Approving a message template shall unblock every campaign depending on it, and un-approving or withdrawing a template shall re-block them, evaluated from the template's current state rather than from a copied flag on the campaign. | `channels`; B10 tab 3 → tab 4 | MUST | Approve `appointment_confirmation`: its campaign becomes enableable in the same read. Withdraw the approval: the campaign returns to `Blocked` and, if enabled, stops sending. The campaign record holds no duplicated approval state. *(Cross-module invariant; also listed in [`cross-module.md`](./cross-module.md).)* |
