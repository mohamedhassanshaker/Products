# 5.11 `verification` — providers, step-up, identity stitching (B11 tabs 1, 2, 5)

| ID | Requirement | Source | Pri | Acceptance criteria |
|---|---|---|---|---|
| FR-VERI-01 | The system shall maintain a verification provider registry containing at minimum a national digital identity provider, an OTP possession factor and a document check, each independently enabled or disabled. | B11 tab 1 | MUST | UAE PASS, OTP to registered mobile and Emirates ID scan render with their seeded states (on, on, off). Disabling a provider removes it from step-up satisfaction paths immediately. |
| FR-VERI-02 | The system shall obtain, from the national digital identity provider, a verified name, an Emirates ID hash and a mobile number, and shall store the hash rather than the identifier. | B11 tab 1 | MUST | No raw Emirates ID value is persisted anywhere. The stored hash is salted per deployment and is not reversible. The mock adapter returns the same field shape as the real one. |
| FR-VERI-03 | The system shall fall back to the OTP possession factor when the national identity provider is unavailable, and shall record which provider satisfied a verification. | B11 tab 1 | MUST | With the identity provider unavailable, verification completes by OTP and the assurance record names the provider used. With both unavailable, the gated action is refused, never allowed through. |
| FR-VERI-04 | The system shall provide an account-ownership check that verifies the citizen owns the account number they supply. | B11 tab 1 | MUST | The toggle persists per tenant. Its state is visible on the transaction and conversation records created while it was set. |
| FR-VERI-05 | The system shall refuse any lookup, linkage or payment against an account the citizen does not own while the account-ownership check is enabled. | B11 tab 1 `[rule]` | MUST | With the check on, supplying another person's account number is refused before any tool call and the attempt is recorded. With it off, the wider access is possible and the configuration change that permitted it is audited. This is the single most consequential toggle in the system and has a dedicated negative test. |
| FR-VERI-06 | The system shall define assurance levels and shall map each gated action to a required level: `L0` anonymous allowed, `L1` verified identity required, `L2` verified identity plus OTP, `L3` document-verified. | B11 tab 2; ADR-0006 | MUST | Viewing a bill balance requires L0; linking a utility account requires L1; initiating a payment and changing a registered mobile require L2. **[ASSUMPTION]** — B11 tab 2 lists four gated actions across three distinct levels while ADR-0006 refers to four levels; L3 is defined here to carry the Emirates ID document check used by kiosk journeys, and is not required by any seeded action. See [`risks.md`](./risks.md) RISK-006. |
| FR-VERI-07 | The system shall evaluate and satisfy the required assurance level before making the tool call that performs a gated action, never after. | B11 tab 2 `[rule]` | MUST | A call-ordering test fails if the payment tool is invoked before the L2 assurance record exists. The assurance record's timestamp precedes the tool invocation on the trace. |
| FR-VERI-08 | The system shall verify through a `VerificationProvider` port, and the mock adapter shall implement every assurance level and be drivable to any state by a test. | ADR-0006 rule 5 | MUST | The step-up test suite runs entirely against the mock and exercises L0–L3, success, failure, timeout and provider-unavailable. The same suite is the acceptance suite for the real adapter, unchanged. |
| FR-VERI-09 | The system shall refuse to start when a mock verification adapter is configured in a production environment. | ADR-0006 rule 6 | MUST | Booting with the mock adapter and `environment=production` exits non-zero with a message naming the conflict. No configuration override bypasses this. |
| FR-VERI-10 | The system shall configure cross-channel identity stitching with an on/off setting and a stitching key selected from a verified identity hash, a mobile number, or never stitch. | B11 tab 5 | MUST | All three key options are selectable, defaulting to the verified identity hash. `Never stitch` prevents any join between sessions. |
| FR-VERI-11 | The system shall stitch only verified sessions, and shall never merge an anonymous session into a verified identity. | B11 tab 5 `[rule]` | MUST | An anonymous web session and a verified WhatsApp session sharing a mobile number remain separate. Only two verified sessions with a matching key are joined. This has a dedicated negative test. |
| FR-VERI-12 | The system shall configure conversation memory scope as per verified identity, per channel session, or no memory. | B11 tab 5 | MUST | All three scopes are selectable, defaulting to per verified identity. Under `no memory` no cross-turn recall persists beyond the active session. |
| FR-VERI-13 | The system shall configure memory retention from 30 days, 90 days or 1 year, defaulting to 90 days, and shall purge memory beyond the configured period. | B11 tab 5; B14 tab 4 | MUST | Derived memory older than the configured period is absent after the purge job runs. **Retention is now a single authority** — see [`risks.md`](./risks.md) RISK-022: `IdentityStitchingConfigs.memoryRetentionDays` is retired, and [`governance.md`](./governance.md) FR-GOV-23's `PrivacyConfigs.transcriptRetention` drives `Conversations.retentionExpiresAt` directly. This module keeps only the scope control (FR-VERI-12). |
| FR-VERI-14 | The system shall carry the current assurance level on the `Principal` so feature modules can gate on it without knowing how it was established. | ADR-0006 rule 1 | MUST | Feature modules read an assurance level and never a provider name, token or claim. The handover context rail ([`handover.md`](./handover.md) FR-HAND-04) and the payment gate ([`payments.md`](./payments.md) FR-PAY-06) both read the same field. |
